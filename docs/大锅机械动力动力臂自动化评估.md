# 大锅「动力臂」全流程交互评估

> 日期：2026-11-08  
> 范围：评估 Create 动力臂（Mechanical Arm）与机械手（Deployer）对大锅的投料、返还物和锅盖能力。正文保留最初评估，文末补充 2026-11-09 已实现范围。

## 结论

**可以做，而且比原有评估简单：调料容器实际只会产生一个返回栈；难点在返回栈的安全路由和无人值守投料顺序。**

按难度拆分：

| 环节 | 难度 | 判断 |
|---|---:|---|
| 普通食材投入 | 低 | 现有 `BigPotItemHandler` 已从顶面暴露物品能力，动力臂可直接投放 |
| 盐等无容器调料 | 低 | 复用现有投料入口即可，但规则要统一到自动化入口 |
| 瓶装 / 碗装调料 | 低到中 | 现有 `getCraftingRemainingItem()` 只返回一个返回栈：未用完的调料瓶（带耐久）或空玻璃瓶；碗装调料返回碗。主要工作是放宽 `dropIn` 并把返回栈送入相邻物流 |
| 盖上锅盖 | 低到中 | 需要新增专用交互点，把锅盖物品转成 `Pot.LID` 状态 |
| 从混合仓自动完成整锅菜 | 高 | 动力臂没有配方状态机；投错或投满时会拿着物品卡住，需要分仓、过滤或多臂分阶段 |
| 自动盛出成品 | 高（若“全程”包含） | 当前物品能力只收不出，且盛菜需要先放碗/大盆，属于另一个交互闭环 |

**推荐判断：** 如果只要求“动力臂把已分拣好的食材送进锅、最后盖盖”，属于中等工作量；如果要求“一只动力臂从混合仓拿所有食材和调料，自动判断顺序并完成一锅”，不建议直接做，稳定性和容错会明显变差。

## 当前代码基础

- `BigPotItemHandler#insertItem()` 已把大锅包装成只进不出的 `IItemHandler`，从顶面接收物品，供溜槽、漏斗和动力臂使用。
- `BigPotCooking#dropIn()` 是自动化投料入口，目前明确拒绝所有带合成剩余物的物品，并且除盐以外的调料都不收。因此瓶装酱油、醋、油和碗装大酱现在都不能通过动力臂投放；要支持它们，需要放宽这个入口并让调用方处理 `remainderOf()`。
- `BigPotItemHandler#extractItem()` 永远返回空，自动化无法从锅里取出成品。
- 锅盖目前只能在 `BigStoveBlock#useItem()` 的玩家右键路径里放上去；普通物品能力不认锅盖，也不负责改 `Pot.LID` 方块状态。
- 动力臂的每个交互点只有 `DEPOSIT` / `TAKE` 两种模式，并不存在“执行一次右键”的通用语义。普通投料可以复用现有顶面 `IItemHandler`；只有锅盖这种方块状态操作需要自定义 `ArmInteractionPointType`。

## 各环节说明

### 1. 普通食材

可以沿用现在的物品能力。动力臂把食材从箱子送入大锅，实际会走 `BigPotCooking#dropIn()`，一次收一个，满足“锅里有水、没开煮、没放满”等条件。

需要注意的是，现有 `full()` 只检查全局最大食材/调料数量，不检查“再加入这一份后是否仍有配方可匹配”。自动化连续投料时，很容易把一锅目标菜投成谜之炖菜，或者把某种配料投多。

### 2. 瓶装 / 碗装调料

这里原来的“剩余调料 + 空瓶/碗两个返回物”判断需要修正。实际实现中，`SeasoningBottleItem#getCraftingRemainingItem()` 的返回值只有一个：

- 还没用完：返回同一个调料瓶，耐久值扣除本次剂量；
- 最后一次用完：返回空玻璃瓶；
- 碗装辣椒酱、大酱等：返回一个碗；
- 水盆、水桶：返回空大盆、空桶，仍然走水量分支。

因此 `BigPotItemHandler#insertItem()` 的单个返回栈足够表达，不需要新增“剩余调料槽 + 空容器槽”。真正要补的是：`BigPotCooking#dropIn()` 不再一刀切拒绝带合成剩余物的物品，允许瓶装/碗装调料进入，并把 `remainderOf()` 的结果交给调用方；调用方再尝试送入相邻库存，送不进才安全弹出。

这仍然不是“零改动”：还要处理返还瓶被掉落物入口再次接住、相邻接收器就是本次输入来源、以及没有接收器时的安全落点。但不需要为每个配方维护两套输出状态。

### 3. 锅盖

动力臂不能直接把锅盖物品“放进方块状态”。需要新增专用交互点：

- `DEPOSIT` 模式：手里是锅盖且锅处于 `Pot.POT` 时，把锅盖存入大锅并改成 `Pot.LID`。
- `TAKE` 模式：把锅盖取回动力臂，再输出到箱子。

一个交互点同一时间只有一种模式，所以投盖和取盖不能共用同一个点。大灶是 2×2 四格，可以分别在两格布置“投盖点”和“取盖点”，由同一只动力臂轮流访问；也可以使用两只臂。实现本身不复杂，难的是确保盖盖发生在料齐之后。

### 4. “全程”顺序控制

动力臂没有配方预览，也不会因为“这一份投不进去”自动换一种物品。它的实际行为是：

1. 从输入点取出一整栈物品；
2. 在输出点逐一试投；
3. 如果没有任何点接受，它会一直拿着这栈物品，无法回去换料。

因此，单只动力臂从“食材、调料、锅盖混装的一个箱子”里取料并不可靠。投入顺序稍有偏差，就会卡在手里，或者把可以成菜的原料投成谜之炖菜。

推荐的落地形态是：

- 水由注液器、管道或水桶专用输入完成；
- 食材和调料分箱、过滤，必要时分臂；
- 锅盖单独用一个受红石控制的动力臂或机械手，等投料结束后再盖；
- 在 `insert()` 前增加“本次投料后仍存在候选配方”的检查，而不是只数总格数。

### 5. 成品取出

如果“全程”包含盛菜，则还需要额外设计：

- 当前 `extractItem()` 不会返回成品；
- 盛菜要求先提供碗或大脸盆，而动力臂一次只能处理一个物品栈；
- 更合适的做法是增加专用出菜槽/出菜交互点，或者在成品阶段用机械手右键盛装，而不是把整套逻辑塞进一个通用动力臂交互点。

## 建议的实现顺序

若后续决定实现，建议按下面顺序拆：

1. 先补“投料后仍能匹配至少一条配方”的防过量检查。
2. 新增仅在大灶上生效的高优先级 `ArmInteractionPointType`，先只支持普通食材和盐。
3. 增加锅盖的 `DEPOSIT` / `TAKE` 两个交互点，验证 2×2 四格中的点位选择。
4. 放宽 `dropIn` 接受瓶装/碗装调料，并把 `remainderOf()` 交给相邻库存；只有没有接收器时才安全弹出。
5. 最后评估成品自动取出，把盛菜与投料分开设计。

## 2026-11-09 剩余物送入相邻物流的可行性

**结论：可以做，建议按“放宽投料入口 + 返还物路由 + 防回流”三步实现，难度低到中；这部分不需要 Create 专属代码。**

### 1. 投料入口

`BigPotCooking#dropIn()` 当前的两个限制需要拆开：

- `stack.hasCraftingRemainingItem()` 目前一刀切拒绝，导致瓶装和碗装调料进不了这条自动化通道；水盆走前面的水量分支，已经能投，但仍需要统一返还物路由；
- `seasoning && !stack.is(SALT)` 目前只允许盐，其他调料不符合。

建议只对“可识别的调料”放宽：瓶装/碗装调料必须先在 `BigPotRecipes` 或 `MysteryStew` 的调料标签中匹配，非调料且带合成剩余物的物品继续拒绝。`simulate` 分支必须只做判断，既不写锅，也不生成或路由返还物。

### 2. 返还物路由

一次成功投料后，`remainderOf()` 已经能给出唯一返回栈：

- 水桶 / 水盆：空桶 / 空大盆；
- 瓶装调料：剩余耐久的调料瓶，最后一次用完则是空玻璃瓶；
- 碗装调料：碗。

把 `BigPotItemHandler#insertItem()`、`BigStoveBlock#stepOn()`、`BigStoveBlock.PotInput#setChanged()` 三处的 `popOut()` 统一改成“先尝试相邻库存，失败再弹出”。路由时枚举大灶 2×2 占地周围的可用面，排除大灶四格自身，避免把物品又塞回同一口锅。

### 3. 相邻接收器

已核对 Create 6.0.10（1.21.1）和 6.0.8（1.20.1）：

- `ChuteBlockEntity` 暴露 `ChuteItemHandler`，实现 `IItemHandler`；
- `BeltBlockEntity` 暴露 `ItemHandlerBeltSegment`，实现 `IItemHandler`；该段被占用或输入方向不允许时会正常拒绝插入，传送带未启动时可能只是暂存、不会立即运走；
- 原版漏斗、箱子等容器也可通过标准物品能力接收。

实现时使用加载器通用物品能力即可：1.21.1 走 `Capabilities.ItemHandler.BLOCK`，1.20.1 走 `ForgeCapabilities.ITEM_HANDLER`，不需要把 Create 变成硬前置。Create 的 `FunnelBlockEntity` 本身不是库存，不能把“贴着大灶的漏斗本体”当成直接接收器；应让漏斗背后的容器接收，或另做专门的 Create 兼容。

### 4. 必须防的两个回流问题

- **返还瓶被 `stepOn` 再次接住**：瓶装调料的剩余瓶仍然能被 `dropIn` 接受；如果没有相邻接收器而直接在锅口弹出，下一轮 `stepOn` 可能连续消耗它。没有接收器时应弹在锅口半径之外（例如灶边），或给该掉落物加一次性的防自动投料标记，不能原地弹回锅口。
- **返还物回到本次输入来源**：动力臂/溜槽从上方送入时，如果相邻搜索又把剩余瓶送回同一个溜槽，就可能形成闭环。路由应排除本次输入面/来源方块；排除后仍没有接收器时按上一条安全弹出。

### 5. “用去一份”的边界

`BigPotItemHandler` 每次 `insertItem` 只消耗一个物品，符合“一份”的语义。`stepOn` 目前会沿着一整摞物品循环投料到锅满或无法再收；若要求掉落物接触一次只消耗一份，应把 `stepOn` 改成单次投料并保留剩余物品栈，否则一瓶/一碗的返还物会按整摞连续结算。

### 6. 调料单位应当是“份”，不是配方里的 mB

`BigPotRecipe.Entry` 的 `count` 对大锅调料已经是“份数”：`BigPotRecipes.maxSeasonings()` 和配方匹配都按这个整数累加，不需要再给每条配方单独写 `amount`。对 `SeasoningBottleItem`，一份固定是 `DOSE_MB = 50` mB；瓶容量 `CAPACITY_MB = 250` mB，也就是 5 份。碗装调料、盐等固体调料则是一个物品 = 一份。

**不建议**把每条配方的调料用量写成可变的 `amount`。如果配方要 2 份，直接写 `count: 2`；如果要 25mB 这种不是 50 的整数倍的量，应该换成另一种“份量物品”或改用流体配方，而不是让同一个瓶装物品承担任意毫升数。否则配方匹配、JEI 展示和自动化投料都会出现“半份算不算一份”的歧义。

评估时存在的精确性缺口已经补上：`SeasoningBottleItem.useOnce()` 原本会无条件加 50mB，若瓶内只剩 30mB，`use()` 会直接返回玻璃瓶并把这 30mB 当成一份。现在自动化入口统一先检查 `hasPortion()`（`remainingMb >= DOSE_MB`），不足一份时拒绝投料并保留原瓶；实际扣除走 `consumePortion()`。

多份配方还有物流要求：`count: 2` 需要连续成功投料两次。同一瓶第一次用完后返还的剩余瓶必须再次进入投料口；如果只是把返还物送到相邻输出线，它不会自动完成第二份，除非那条输出线又把它送回输入缓冲区。需要在“相邻输出”之外另外定义输入回流或整瓶批量消耗策略。

## 风险

- **双版本 API 差异**：Create 6.0.8（1.20.1）和 6.0.10/6.0.11（1.21.1）的注册表、物品能力包名不同，Stonecutter 分支必须分别编译。
- **可选前置**：所有 Create 类都必须放在 `compat/create` 隔离目录，只在 `OptionalMods.create()` 为真时加载，不能影响未安装 Create 的存档。
- **存档兼容**：新增交互点类型会写进动力臂 NBT；卸载模组或回退版本时要保证未知类型能被安全跳过。
- **回归面**：现有溜槽、漏斗、机械手投料、手动右键投料、锅盖反悔期、Jade 和 JEI 都要一起回归，不能只测动力臂。

## 一句话回答

**普通食材、锅盖、水盆、瓶装/碗装调料都能做；调料容器实际只有一个返还栈，关键是放宽 `dropIn`、把返还物送入相邻库存，并避免返还瓶被锅口再次自动消耗。真正困难的仍是让一只动力臂在混合仓里稳定判断投料顺序；若限定为分拣后的投料加自动盖盖，难度中等；若要求单臂全自动闭环，难度高，不建议按最小改动硬塞。**

## 2026-11-09 实现：整份扣除与返还物路由

前面列出的三个关键缺口已经落地：

1. **不足一份拒绝**：`SeasoningBottleItem#hasPortion()` 检查剩余量是否至少 50 mB；右键和自动化入口都先经过这个检查。不足一份的瓶子保留原样，不再被 `use()` 吞掉余量。大缸 `perDose` 入口也加了同一检查。
2. **自动化接受调料**：`BigPotCooking#dropIn()` 现在接受所有配方 / 谜之炖菜认的调料，包括瓶装酱油、醋、油和碗装辣椒酱、大酱；非调料且带合成剩余物的物品仍拒绝。成功投料返回唯一的剩余瓶、空玻璃瓶、碗或空桶 / 空盆。
3. **返还物路由**：`BigPotItemHandler#insertItem()`、`BigStoveBlock#stepOn()`、`PotInput#setChanged()` 统一调用 `BigPotCooking#output()`。优先送入大灶 2×2 四邻或下方的库存；排除大灶自身与另一口大灶；不向上搜索，避免直接返还到顶部输入。没有接收器时在锅口正前方 1.35 格处安全弹出，不再落回锅口被连续接住。
4. **机械手（Deployer）右键返还**：机械动力机械手使用假玩家走 `BigStoveBlock` 右键路径。假玩家投瓶装 / 碗装调料或倒水桶 / 水盆后，返还物同样交给 `output()`，不再塞进假玩家背包；没有相邻库存时从锅口外沿弹出。
5. **动力臂（Mechanical Arm）直接投料**：新增 `CreateArmCompat` 与 `northeast_china_delight:big_pot` 交互点。动力臂不使用假玩家，而是通过 `DepositOnlyArmInteractionPoint` 调用大锅顶面的 `BigPotItemHandler`。交互点只认大灶西北角且 `Pot.POT` 的状态，一口锅一个点，优先级 100，动画目标为锅口中心。1.21.1 用 `DeferredRegister` 注册，1.20.1 在 `RegisterEvent` 注册，避免 common setup 时注册表已冻结。

**尚未实现的边界：** 动力臂目前只做投料，不能放 / 揭锅盖，也不能盛菜；交互点不读配方状态，因此单只动力臂从混合仓连续投料仍可能投多或把菜投成谜之炖菜。需要全自动闭环时，仍应使用分仓、过滤器或额外状态机。

**多份配方的边界仍然保留：**一次成功投料只加一份。`count: 2` 需要两次投料，自动化必须让第一次返还的剩余瓶再次进入输入口；本实现不在单次 `insertItem()` 中隐式按整瓶批量扣量。这样 “count = 份数” 和 “一次 = 一份” 的语义始终一致。

构建与产物记录见 `docs/项目结构与资源索引.md` §110、§111；实机回归见 `docs/回归测试表.md` BP-18~BP-24。

## 2026-11-09 实现：动力臂盖锅盖与比较器进度

动力臂盖锅盖已按“自定义交互点覆写插入”的方案落地，没有把锅盖塞进普通食材能力：

- `BigStoveBlock#placeLid` 抽出统一安装路径，玩家右键和动力臂共用方块状态更新、锅盖原样保存、`BigPotCooking#lidPlaced`、音效与 GameEvent；
- `BigPotPoint#insert` 只拦截 `ModItems.BIG_POT_LID`，交给 `BigStoveBlock#insertLid`；`simulate` 不产生副作用，成功一次只放一枚，余量原样返回；
- 非锅盖仍走 `DepositOnlyArmInteractionPoint` 原来的 `BigPotItemHandler` 投料路径，返还物路由不变；
- 交互点仍只在西北角 `Pot.POT` 时存在，盖好后变为 `LID`，因此动力臂当前只能盖盖，不能揭盖、拿锅或盛菜。

比较器部分也已实现：空闲为 0，三秒等待 / 刚开煮为 1，烹饪中按 `cookProgress / cookTotal` 输出 1–14，完成且有成品为 15。`BigPotBlockEntity#syncComparator` 只在档位变化时通知，`BigStoveBlock#updateAnalogOutput` 同步 2×2 四格，比较器贴任意一格都能刷新。它是模拟信号，不能用只输出 0/15 的红石中继器替代。

仍需实机确认：动力臂在目标点失效后的重新选点、锅盖附魔 / 耐久保留、比较器贴非西北格、揭盖与灭火后的读数保持、盛完最后一份归零。回归项见 BP-25 / BP-26 与 R-67 / R-68。
