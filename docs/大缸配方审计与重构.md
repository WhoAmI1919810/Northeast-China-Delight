# 大缸配方审计 + 重构方案（2026-09-24）

> 以下是 2026-09-24 的历史审计/设计快照，其中旧配方的“天数”和 Java 硬编码位置不代表当前版本。2026-10-12 已将 14 条大缸配方迁至 `data/northeast_china_delight/recipe/vat/*.json`，ID 取资源路径，并通过 RecipeManager 与 JEI 同步；覆盖与禁用方法见 `docs/大缸配方数据包用法.md`，当前配方用量、时长以 JSON 为准。

## 1. 为什么要重构

同一套配方规则现在**写在三个地方**，所以每次改配方都要改三遍，漏一处就出 bug：

| 位置 | 写的是什么 |
| --- | --- |
| `block/Vat.java` | 能不能放、放多少、什么时候开始、完成后怎么变（一大堆 switch） |
| `crafting/VatRecipes.java` | 常量 + 时长 + 各种 `xxxInput()/xxxResult()` 取值函数 |
| `compat/jei/VatJeiRecipes.java` | JEI 页面里再手写一遍"投料 / 工具 / 产物 / 时长" |

目标：**一条配方 = 一条声明**（投料、工具、液体、时长、完成后的变化），交互逻辑和 JEI 都从这份声明生成。

## 3. 找出来的逻辑错误

### 3.1 严重 / 会被玩家利用

1. **酸引水能当"水"腌菜，导致液体翻倍。**
   `VatBlockEntity#refreshSourWaterLevel()` 把酸引水按 `ceil(mB/1000)` 折算成**方块状态的水位**，
   而泡菜/辣白菜开始的条件只看水位 > 0。于是：倒 1 瓶酸引水（250 mB）→ 显示 1 层 →
   放白菜+盐+石头就能腌 → 腌完 `addSourWater(层数×1000)` → **250 mB 变 1250 mB**。

2. **酸引水能倒进装了水的缸里混装。**
   `canPourSourWater(NONE)` 只检查"没内容物、没成品液体"，不看水位。
   3 层水的空缸照样收酸引水，然后 `refreshSourWaterLevel()` 按酸引水重新写水位 →
   **水位从 3 掉到 1，缸里的水凭空消失**。

3. **白醋一次清空全部酸引水。**
   配方只要 750 mB，但 `finishVinegar` 前调用的是 `setSourWaterMb(0)`：
   一缸泡菜腌完能有 3000 mB（12 瓶），酿一次白醋**全没了**，只剩 10 瓶白醋。

### 3.2 配方本身不合理

4. **酿醋不用水**（用户指出）：3 酱渣 + 3 谷物 + 布 → 10 瓶醋，缸里全程没有任何液体。
5. **Kind.DOUGH 是死配方**：旧的"水面团"流程早已删除，但 `Kind.DOUGH`、
   `doughInput/doughResult/resultFor`、`totalUnits`、`drainsWater`、取货分支都还在。
6. **加水被 `FERMENTED` 挡住**：注释写的是"只要不在处理中就能加水"，代码却是 `!FERMENTED`。
   酿完大酱/酱油的缸（FERMENTED=true、缸里还剩酱渣）**加不进水**，
   一旦醋需要水，这条路会被直接堵死。

### 3.3 体验 / 一致性问题

7. **液位显示粒度**：1 瓶（250 mB）就显示成 1 整层（1000 mB）。方块模型只有 0~3 层，
   这个是硬限制；Jade 里显示的是准确 mB，两者的差异要在提示里说清楚。
8. **腊肉 / 咸鱼要求盐数"严格等于"肉数**：盐放多一份就永远不启动，玩家只能继续加肉。
   这是刻意的"配平才开工"设计，但按石头时只有一句笼统的 `materials_not_ready`，
   应该提示"盐 3 / 肉 3 才配平"。
9. **倒酸引水进"正在腌的泡菜缸"**：`canPourSourWater(PICKLE) = true` 无条件放行，
   会把正在腌的一缸盐水污染成酸引水缸。
10. **取酱渣的分支残留**：`VINEGAR` 现在不产酱渣了（本轮已改成消耗），取货分支还留着。

## 4. 重构方案：声明式 VatRecipe

一条配方 = 一个 `VatRecipe`，字段如下（全部是"数据"，没有 if/switch）：

```
kind        配方对应的 Kind
seal        封口方式：NONE / PRESS(压缸石) / CLOTH(粗布毯) / CARPET(羊毛地毯)
water       需要的水位区间（min~max 层，0 表示不要求），或
sourWater   需要的酸引水量（mB）
slots       投料格：每格 = 匹配器 + 数量下限 + 数量上限 + 完成后的去向
seconds     基准时长（秒），perLayer=true 时按水位翻倍
onComplete  完成后：产出什么液体、水位怎么变、酸引水怎么变
startFrom   允许从哪些 Kind 转入（例如酱油可以从大酱缸加小麦转过来）
take        取货规则（保留原样 / 换成成品 / 给一瓶）
```

投料格的"数量"支持三种写法：

* 固定值（大酱的酱块 3 块）；
* 按水位（泡菜每层 2 份菜、1 份盐）；
* 跟随另一格（腊肉的盐数 = 肉数、咸鱼的盐数 = 鱼数）。

格子的"去向"：`KEEP`（留着，取出时按映射给成品）、`CONSUME`（消失）、
`CONVERT`（变成另一个物品，例如酱块→酱渣、玉米粒→酸玉米粒）。

这样一来：

* `Vat.java` 只剩一套通用引擎（找配方 → 判断能不能放 → 判断能不能开工 → 完成后套用变化）；
* JEI 页面从同一份声明自动生成，不会再和游戏内判定不一致；
* 新增配方 = 在注册表里加一条，工具/时长/产物/JEI 全自动。

### 引擎长什么样

* `crafting/VatRecipe.java`：一条配方 = `密封方式 + 液体要求 + 投料格列表 + 时长 + 完成后的变化`。
  投料格的数量规则支持**固定值 / 按水位缩放 / 查表 / 跟着另一格走**四种写法，全是数据；
  格子的去向分四种，覆盖了所有配方：
  * `KEEP`：留在缸里，取货时按换算规则给成品（泡菜、腊肉、咸鱼）；
  * `CONVERT`：完成时变成另一样东西（酱块→酱渣、黄豆→豆芽、玉米粒→酸玉米粒）；
  * `CONSUME`：完成时就没了（酱油用的小麦、酿醋的谷物、格瓦斯的面包）；
  * `ABSORB`：完成时**还留在缸里影响颜色**（盐水让肉发白、辣椒酱让水发红），取货时才消失；
* `crafting/VatRecipes.REGISTRY`：13 条配方全部是声明式的一条数据，带 `priority`；
* `crafting/VatBrewing.java`：只做四件事 —— `forInsert`（放这份料会变成哪条配方）、
  `ready`（现在能开工的是哪条）、`complete`（按 `Fate`/`LiquidAfter` 套用变化）、`takeOne`（按格子取货）。
  **这个文件里没有任何一个具体物品的名字。**

### 选配方怎么选（重叠时不再靠 if）

打分顺序：**满足的格子数 → 能不能开工 → 本来就是这条 → 液体对得上 → 要求的总份数少 → priority**。

* 大酱缸加小麦 → 酱油（酱油多满足一格）；
* 泡菜缸加辣椒酱 → 辣白菜（辣白菜多满足两格，即使泡菜"现在就能开工"也让位）；
* 5 条鱼 + 3 份盐还是咸鱼，第 6 条鱼当场转鱼露（鱼露那一条这时正好齐了）；
* 泡菜腌完、缸里有 3 份酸引水时加谷物 → 白醋；酱渣 + 谷物 → 醋。

### 行为变化（有意为之）

* 往缸里放料**不再有先后顺序的坑**：先放盐后放肉、先放菜后放盐都能成（数量没配齐就不开工）；
* 反过来，材料配错也不会"卡死"：拿不准就按空缸处理，随时可以取出重来；
* 鱼露 / 虾酱瓶倒进辣白菜缸时**只还一个空瓶**（以前投料还一个、取货又还一个，一瓶鱼露能刷出两个玻璃瓶）；
* 白醋酿完后剩下的酸引水可以用玻璃瓶继续装出来（以前会永远留在缸里取不出）。

| 编号 | 问题 | 症状 | 修法 |
| --- | --- | --- | --- |
| P1 | 做好的缸不能再投料 | `forInsert` 把 `PROGRESS > 0` 当成"正在发酵"，而完成时 `complete` 会把 PROGRESS 写成 `MAX_PROGRESS` —— 于是**所有做完的缸都投不进新料**：回归清单 #7（酱渣→醋）、#8（酸引水→白醋）以及第 6 章的"大酱加小麦→酱油"在游戏里都做不到，只能把料取出来重新放一遍 | `processing = PROGRESS > 0 && !FERMENTED` |
| P2 | 盖布的先后顺序会把人卡死 | 加水分支与倒酸引水分支都不调用 `tryStart`，所以"先盖盖布、后倒水"永远不开工；而未发酵的蒙盖缸空手右键被 `!FERMENTED → PASS` 挡住，**盖布取不回来，只能砸缸** | 两个液体分支补 `tryStart`；`useWithoutItem` 里盖布与压缸石同样对待（随时可取回，没腌好就清零进度重来） |
| P3 | JEI 上的盐数算错 | "盐数 = 肉数"（`sameAs`）在 JEI 那份 `Counts` 里靠 `Predicate` 引用相等认亲，不同调用点的 lambda 是不同对象 → 算成 0，再被钳成 1：JEI 写"6 肉 + 1 盐"，游戏里要求 6 + 6 | 跨格引用改成**槽位号**（`sameAs(slotIndex, ratio)` + `Counts#countOfSlot`），JEI 与游戏共用 `VatRecipe#displayedCounts` |

## 8. 状态空间与卡死复审（2026-10-18）

**配方数量不会进入方块状态。** 大缸的 `BlockState` 只有四个维度：
`WATER_LEVEL`（0~3，4 种）、`FERMENTED`（2 种）、`SALTED`（2 种）、`PROGRESS`（0~20，21 种），
合计 **4 × 2 × 2 × 21 = 336 种组合**。配方只影响方块实体 NBT 里的 `kind` / `recipeId`、
内容物和成品液体，所以从 15 条配方加到更多配方，不会让方块状态线性膨胀，也不会因为状态太多而卡死。

真正需要防的是「某个 NBT + BlockState 组合没有出口」。正常流程的出口包括：
投料、倒水、封口开工、定时 tick 推进、完成、揭封、空手取固体、容器取液体、破坏方块。
本轮按这些出口逐条检查，确认并修复了四处会把人困住的状态：

| 编号 | 风险 | 触发方式 | 修法 |
| --- | --- | --- | --- |
| S-01 | 成品液体两套记账 | `complete()` 只写 `brewedFluid` / `brewedMb`，`hasBottledProduct()` 却只看旧的分液体字段。成品没取完时仍能投下一道料或加水，之后液体可能被新配方覆盖 / 取不出 | `VatBlockEntity.hasBottledProduct()` 同时检查新旧字段；`ready()`、`sealRecipe()`、`forInsert()`、`canContinueWithWater()` 统一走它；旧存档在 `load` 时把分液体字段迁移到统一成品槽 |
| S-02 | 发酵中加水超过 `water_max` | 豆芽只要 1 层水、冻梨 / 冻豆腐只要 0 层水；旧逻辑只要还没 `FERMENTED` 就允许继续倒水，超过上限后 `ready()` 返回 null，tick 不再排程 | `canAddWater()` 在已绑定配方（`recipeId != null` 或 `PROGRESS > 0`）时按当前配方的 `waterMax` 拒绝超量；封口后、第一次 tick 前也算“已开工” |
| S-03 | 进度停在大于 0 但配方失配 | 数据包改配方条件、群系温度变化、或历史异常存档；`tryStart()` 因 `PROGRESS > 0` 永远提前返回，tick 又因 `ready() == null` 不再排程 | tick 和任何一次大缸交互都会检查：`PROGRESS > 0` 且当前无配方匹配时，退回 `PROGRESS = 0` 并解除 `recipeId` 绑定；配方被删除的情况保留原状态，继续走空手返还原料 |
| S-04 | 未开工的封口物取不回 | 盖了布 / 压了石但材料没齐，普通空手右键被 `!FERMENTED` 分支挡住，只能猜 Shift 右键或砸缸 | 未开工（`PROGRESS == 0` 且无配方绑定）时空手右键直接取回封口物；已开工仍只显示进度，Shift 右键才中断 |

**回归结果（2026-10-18）：** `:1.21.1:runGameTestServer` 共 94 项，新增的
`finishedProductBlocksFollowUpUntilDrained`、`processingVatRejectsWaterBeyondRecipeLimit`、
`stalledProgressReturnsToZeroOnInteraction` 全部通过；原有
`soySauceResidueStaysForNextRecipe`、`coverComesBackBeforeFermented` 已由失败转为通过。
剩余 5 项失败为人参种植、潜行摆菜、咸腊肉 JEI 份数（2 项）、箱子默认名单，与本轮大缸状态机改动无关。
1.20.1 独立树 `compileJava + processResources` 通过；其 `runGameTestServer` 在 Create 的
`CustomItemUseEffectsMixin` refmap 处启动失败，属于开发环境依赖问题，未进入测试执行阶段。

## 9. JEI 泡菜拆页回归（2026-10-19）

**问题：** 酸菜和辣白菜在 JEI 里看起来是同一张配方，且只显示蔬菜，看不到盐、辣椒酱、鱼露/虾酱。

**根因：** `VatJeiRecipes` 把泡菜按蔬菜拆页时，用 `only` 过滤了**所有**输入格。
拆页样本是白菜，于是盐格、辣椒酱格、鱼露/虾酱格都被过滤成空列表；两页只剩同一个蔬菜格。
玩家照着 JEI 投料时不会放盐和调味品，配方自然无法开工。

**修法：** 只收窄发生拆分的蔬菜格，其他输入格保留完整候选；按“输入蔬菜 → 产物”分组，
同一产物的多个蔬菜变体仍放在同一页滚动展示，并保证页面 id 不重复。

**回归：** 新增 `vatJeiPicklePagesKeepAllIngredients`，校验酸菜页保留 1 个调味格、
辣白菜页保留 3 个调味格，且两页 id 不同；另新增 `vatPickleCanBeMade`、`vatSpicyPickleCanBeMade`，
从投料、封口、完成到取出成品完整走通。1.21.1 全量 97 项测试中这三项均通过；
剩余 5 项仍是既有问题（人参种植、潜行摆菜、咸腊肉 JEI 份数 2 项、箱子默认名单）。
主树 1.21.1 / 1.20.1 与独立 1.20.1 树均已编译通过。

## 10. 为什么大缸反复出 bug，以及“一劳永逸”的收口方案（2026-10-19）

### 10.1 结论

大缸的问题不是“配方太多”或“BlockState 太多”。真正的原因是：**同一份业务事实被存成了多套表示，又被多个入口分别解释。**

当前至少存在这些重复表达：

| 业务事实 | 现存表示 | 风险 |
| --- | --- | --- |
| 水位 | `BlockState.WATER_LEVEL`、`VatBlockEntity.waterMb`、`sourWaterMb`、`waterLayers()` 派生值 | 显示水位和真实液体量可能不同步 |
| 当前工序 | `VatBlockEntity.kind`、`recipeId`、`BlockState.PROGRESS`、`FERMENTED` | 配方被数据包删除 / 替换后，四个字段可能互相矛盾 |
| 成品液体 | `brewedFluid` / `brewedMb`，以及 `pasteMb`、`soySauceMb`、`vinegarMb` 等历史字段 | 新旧存档两套记账，取不出、重复计算、被下一锅覆盖 |
| 能否投料 | `VatBrewing.forInsert()`、`Vat.canAddWater()`、`canPourSourWater()`、`Vat.tryStart()` 各自判断 | 修好投料路径，加水 / 封口 / tick 仍可能走另一套规则 |
| 能否开工 | `VatBrewing.ready()`、`current()`、`sealRecipe()`、`continuationFits()` 各自重新打分 | 同一缸在不同入口得到不同结论 |
| JEI 展示 | `VatJeiRecipes` 从配方表再投影一遍，并维护自己的过滤条件 | 游戏内能做的配方，JEI 可能显示错；JEI 能看懂的，游戏内可能做不了 |

这些字段和入口并非都错，但它们让“状态一致性”变成了每个新功能都必须重新证明一次的事情。于是每加一条配方、改一次取货规则，就可能只修到其中一条路径，另一条路径继续保留旧假设。最近几次问题——成品液体两套记账、发酵中加水超上限、进度失配卡死、泡菜 JEI 过滤所有输入格——本质上都是同一个结构问题。

**结论：可以消灭这一大类问题，但不能承诺绝对零 bug。** 正确目标是：让非法状态在存档加载或自动化测试时集中暴露，而不是等玩家在某个组合操作里踩出来。

### 10.2 目标结构：唯一状态 + 唯一转换入口

核心不是再写一个更大的 `if`，而是把大缸改成一个小型状态机：

1. **`VatState` 作为唯一真相**：保存真实水量、酸引水量、内容物、封口物、当前配方 id、阶段、进度、成品液体。`kind` 不再作为业务主键，最多保留为兼容字段。
2. **`VatTransition` 作为唯一写入口**：所有操作都表示成动作，例如 `INSERT`、`POUR_WATER`、`POUR_SOUR_WATER`、`SEAL`、`UNSEAL`、`TICK`、`TAKE_SOLID`、`FILL_CONTAINER`、`DRAIN_FLUID`、`BREAK`。
3. **单一 reducer**：`apply(state, action, recipeCatalog) -> result`。合法性判断、状态变化、产物结算、返还物都在这里完成；`Vat` 只负责把玩家交互翻译成动作，`VatBlockEntity` 只负责持久化和调用 reducer。
4. **BlockState 只做表现缓存**：`WATER_LEVEL`、`FERMENTED`、`PROGRESS` 可以由 `VatState` 派生，用于渲染、碰撞箱、比较器；业务判定不再读它们。这样即使客户端显示滞后，也不会改变服务端逻辑。
5. **JEI / Jade / Renderer 共用同一套查询函数**：JEI 不再维护独立过滤条件，只调用 reducer 暴露的 `canStart`、`displayCounts`、`availableActions`。
6. **数据包加载时校验**：每条配方在加载阶段检查输入格、数量规则、产物、液体、封口是否自洽；被禁用或删除的配方显式进入 `INVALID` 状态，而不是散落在各处的兜底分支。
7. **存档只保留一套字段**：新格式写入 `VatState`，旧字段通过一次版本迁移转换后删除；不允许长期双写。存档带 `data_version`，以后每次改结构只加一段迁移。

### 10.3 建议的落地顺序

这是核心重构，不建议和普通配方改动混在一起。按可回滚的顺序做：

1. 先加 `VatState` 快照和存档版本号，旧 NBT 只读适配到新状态，暂时不删旧字段。
2. 把 `forInsert` / `ready` / `current` / `sealRecipe` / `canAddWater` / `tick` / 取货的判断逐步搬进 reducer；每搬一个入口，保留旧入口做对照测试。
3. 让 `Vat` 只发动作，`VatBlockEntity` 只调 reducer；删除 `Vat.java` 里重复的准入判断。
4. 让 BlockState、Jade、Renderer、JEI 全部从 `VatState` 派生；删除 `VatJeiRecipes` 里独立的过滤逻辑。
5. 连续运行一个版本确认旧存档迁移无误后，删除 `pasteMb`、`soySauceMb` 等历史字段和 `kind` 的业务判定。
6. 加“全配方 × 全水位 × 各阶段”的属性测试，至少断言：
   - 每个可达状态都至少有一个合法出口；
   - 任何动作失败都不会改变状态；
   - 成品液体没取空时不能接新配方；
   - 配方被删除 / 禁用后状态可恢复；
   - JEI 展示的份数与 reducer 计算结果一致；
   - 旧存档迁移后能继续取货、继续下一道工序。

### 10.4 短期止血

在重构完成前，先做两件低成本的事：

* 给大缸加一个调试命令 / 日志转储，输出 `VatState`、`BlockState`、`recipeId`、`kind`、成品液体和当前匹配到的配方；以后复现时先看这份快照，不再靠猜。
* 每个大缸 bug 必须同时补一条 GameTest：不仅测“修好的那条路径”，还要测它相邻的投料、加水、封口、tick、取货入口。

**一句话：** 大缸现在的复杂度已经从“配方规则”变成了“状态一致性”。继续在 `Vat.java` 里打补丁只能修下一个个案；把状态收成 `VatState`、把转换收成唯一 reducer，才能把这类 bug 一次性压到测试和存档迁移阶段。

## 11. 辣白菜配方收窄与同族预留（2026-10-19）

**结论：辣味腌制配方已收窄为只接受大白菜，同时保留同族扩展入口。**

* `vat/pickle` 普通泡菜总配方不变，仍接受大白菜、雪里蕻、黄瓜、胡萝卜、青萝卜，并按输入分别产出酸菜、腌雪里蕻、酸黄瓜、腌胡萝卜、腌青萝卜。
* `vat/spicy_pickle` 的主料槽改用 `northeast_china_delight:spicy_pickle_ingredients`。当前标签只含 `#c:crops/napa_cabbage`，因此黄瓜、胡萝卜、青萝卜不再能消耗辣椒酱走辣味配方，也不会再生成对应的无收益 JEI 页。
* 转换器由写死的字符串 `spicy_pickle` 扩展为数据驱动对象：`converter.type = mapped`，`entries[]` 按顺序匹配 `ingredient`，命中则取 `result`，未命中原样返还。现有大白菜映射到 `northeast_china_delight:spicy_cabbage`；旧字符串 `pickle` / `spicy_pickle` 继续兼容旧数据包。
* 未来加入辣萝卜、辣黄瓜等同族配方时，只需把原料加入 `spicy_pickle_ingredients` 标签，并在对应配方的 `converter.entries` 补“原料 → 成品”映射；不同产物会让 JEI 按产物自动拆页，不需要改大缸 Java 引擎。
* 回归：新增 `vatSpicyPickleUsesOnlyItsFamilyTag`（大白菜通过，黄瓜 / 胡萝卜 / 青萝卜拒绝）和 `vatMappedConverterSurvivesNetwork`（映射转换器经配方网络同步后仍生效，未命中原样返还）。1.21.1 GameTest 共 99 项，两项新增通过；剩余 5 项为既有失败（人参种植、潜行摆菜、咸腊肉 JEI 份数 2 项、箱子默认名单）。
* 两棵树均已生成对应标签和映射转换器；1.21.1 / 1.20.1 资源中的标签分别转为 `c:` / `forge:`。主树两个版本与独立 1.20.1 树的编译、资源处理均通过。
