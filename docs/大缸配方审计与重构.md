# 大缸配方审计 + 重构方案（2026-09-24）

## 1. 为什么要重构

同一套配方规则现在**写在三个地方**，所以每次改配方都要改三遍，漏一处就出 bug：

| 位置 | 写的是什么 |
| --- | --- |
| `block/Vat.java` | 能不能放、放多少、什么时候开始、完成后怎么变（一大堆 switch） |
| `crafting/VatRecipes.java` | 常量 + 时长 + 各种 `xxxInput()/xxxResult()` 取值函数 |
| `compat/jei/VatJeiRecipes.java` | JEI 页面里再手写一遍"投料 / 工具 / 产物 / 时长" |

目标：**一条配方 = 一条声明**（投料、工具、液体、时长、完成后的变化），交互逻辑和 JEI 都从这份声明生成。

## 3. 找出来的逻辑错误

### 3.1 严重 / 会被玩家利用

1. **酸引水能当"水"腌菜，导致液体翻倍。**
   `VatBlockEntity#refreshSourWaterLevel()` 把酸引水按 `ceil(mB/1000)` 折算成**方块状态的水位**，
   而泡菜/辣白菜开始的条件只看水位 > 0。于是：倒 1 瓶酸引水（250 mB）→ 显示 1 层 →
   放白菜+盐+石头就能腌 → 腌完 `addSourWater(层数×1000)` → **250 mB 变 1250 mB**。

2. **酸引水能倒进装了水的缸里混装。**
   `canPourSourWater(NONE)` 只检查"没内容物、没成品液体"，不看水位。
   3 层水的空缸照样收酸引水，然后 `refreshSourWaterLevel()` 按酸引水重新写水位 →
   **水位从 3 掉到 1，缸里的水凭空消失**。

3. **白醋一次清空全部酸引水。**
   配方只要 750 mB，但 `finishVinegar` 前调用的是 `setSourWaterMb(0)`：
   一缸泡菜腌完能有 3000 mB（12 瓶），酿一次白醋**全没了**，只剩 10 瓶白醋。

### 3.2 配方本身不合理

4. **酿醋不用水**（用户指出）：3 酱渣 + 3 谷物 + 布 → 10 瓶醋，缸里全程没有任何液体。
5. **Kind.DOUGH 是死配方**：旧的"水面团"流程早已删除，但 `Kind.DOUGH`、
   `doughInput/doughResult/resultFor`、`totalUnits`、`drainsWater`、取货分支都还在。
6. **加水被 `FERMENTED` 挡住**：注释写的是"只要不在处理中就能加水"，代码却是 `!FERMENTED`。
   酿完大酱/酱油的缸（FERMENTED=true、缸里还剩酱渣）**加不进水**，
   一旦醋需要水，这条路会被直接堵死。

### 3.3 体验 / 一致性问题

7. **液位显示粒度**：1 瓶（250 mB）就显示成 1 整层（1000 mB）。方块模型只有 0~3 层，
   这个是硬限制；Jade 里显示的是准确 mB，两者的差异要在提示里说清楚。
8. **腊肉 / 咸鱼要求盐数"严格等于"肉数**：盐放多一份就永远不启动，玩家只能继续加肉。
   这是刻意的"配平才开工"设计，但按石头时只有一句笼统的 `materials_not_ready`，
   应该提示"盐 3 / 肉 3 才配平"。
9. **倒酸引水进"正在腌的泡菜缸"**：`canPourSourWater(PICKLE) = true` 无条件放行，
   会把正在腌的一缸盐水污染成酸引水缸。
10. **取酱渣的分支残留**：`VINEGAR` 现在不产酱渣了（本轮已改成消耗），取货分支还留着。

## 4. 重构方案：声明式 VatRecipe

一条配方 = 一个 `VatRecipe`，字段如下（全部是"数据"，没有 if/switch）：

```
kind        配方对应的 Kind
seal        封口方式：NONE / PRESS(压缸石) / CLOTH(粗布毯) / CARPET(羊毛地毯)
water       需要的水位区间（min~max 层，0 表示不要求），或
sourWater   需要的酸引水量（mB）
slots       投料格：每格 = 匹配器 + 数量下限 + 数量上限 + 完成后的去向
seconds     基准时长（秒），perLayer=true 时按水位翻倍
onComplete  完成后：产出什么液体、水位怎么变、酸引水怎么变
startFrom   允许从哪些 Kind 转入（例如酱油可以从大酱缸加小麦转过来）
take        取货规则（保留原样 / 换成成品 / 给一瓶）
```

投料格的"数量"支持三种写法：

* 固定值（大酱的酱块 3 块）；
* 按水位（泡菜每层 2 份菜、1 份盐）；
* 跟随另一格（腊肉的盐数 = 肉数、咸鱼的盐数 = 鱼数）。

格子的"去向"：`KEEP`（留着，取出时按映射给成品）、`CONSUME`（消失）、
`CONVERT`（变成另一个物品，例如酱块→酱渣、玉米粒→酸玉米粒）。

这样一来：

* `Vat.java` 只剩一套通用引擎（找配方 → 判断能不能放 → 判断能不能开工 → 完成后套用变化）；
* JEI 页面从同一份声明自动生成，不会再和游戏内判定不一致；
* 新增配方 = 在注册表里加一条，工具/时长/产物/JEI 全自动。

## 5. 本轮要一起修掉的问题

* 3.1 的三条（酸引水腌菜翻倍、混装丢水、白醋清空全部酸引水）；
* 3.2 的三条（醋加水 1 层并消耗、删掉 DOUGH 死配方、允许给发酵完的酱缸续水）；
* 3.3 的第 9、10 条（不许往正在腌的缸里倒酸引水、清掉取酱渣的残留分支）。

### 引擎长什么样

* `crafting/VatRecipe.java`：一条配方 = `密封方式 + 液体要求 + 投料格列表 + 时长 + 完成后的变化`。
  投料格的数量规则支持**固定值 / 按水位缩放 / 查表 / 跟着另一格走**四种写法，全是数据；
  格子的去向分四种，覆盖了所有配方：
  * `KEEP`：留在缸里，取货时按换算规则给成品（泡菜、腊肉、咸鱼）；
  * `CONVERT`：完成时变成另一样东西（酱块→酱渣、黄豆→豆芽、玉米粒→酸玉米粒）；
  * `CONSUME`：完成时就没了（酱油用的小麦、酿醋的谷物、格瓦斯的面包）；
  * `ABSORB`：完成时**还留在缸里影响颜色**（盐水让肉发白、辣椒酱让水发红），取货时才消失；
* `crafting/VatRecipes.REGISTRY`：13 条配方全部是声明式的一条数据，带 `priority`；
* `crafting/VatBrewing.java`：只做四件事 —— `forInsert`（放这份料会变成哪条配方）、
  `ready`（现在能开工的是哪条）、`complete`（按 `Fate`/`LiquidAfter` 套用变化）、`takeOne`（按格子取货）。
  **这个文件里没有任何一个具体物品的名字。**

### 选配方怎么选（重叠时不再靠 if）

打分顺序：**满足的格子数 → 能不能开工 → 本来就是这条 → 液体对得上 → 要求的总份数少 → priority**。

* 大酱缸加小麦 → 酱油（酱油多满足一格）；
* 泡菜缸加辣椒酱 → 辣白菜（辣白菜多满足两格，即使泡菜"现在就能开工"也让位）；
* 5 条鱼 + 3 份盐还是咸鱼，第 6 条鱼当场转鱼露（鱼露那一条这时正好齐了）；
* 泡菜腌完、缸里有 3 份酸引水时加谷物 → 白醋；酱渣 + 谷物 → 醋。

### 行为变化（有意为之）

* 往缸里放料**不再有先后顺序的坑**：先放盐后放肉、先放菜后放盐都能成（数量没配齐就不开工）；
* 反过来，材料配错也不会"卡死"：拿不准就按空缸处理，随时可以取出重来；
* 鱼露 / 虾酱瓶倒进辣白菜缸时**只还一个空瓶**（以前投料还一个、取货又还一个，一瓶鱼露能刷出两个玻璃瓶）；
* 白醋酿完后剩下的酸引水可以用玻璃瓶继续装出来（以前会永远留在缸里取不出）。
