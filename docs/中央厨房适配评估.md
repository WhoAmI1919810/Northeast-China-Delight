# 中央厨房（Create: Central Kitchen）适配评估

> 评估日期：2026-11-08  
> 评估对象：`https://github.com/DragonsPlusMinecraft/CreateCentralKitchen`  
> 结论范围：只评估适配可行性、接入点和风险；本轮不改功能代码、不构建、不启动客户端、不提交。

## 结论

**可以适配，但不能把“安装中央厨房”理解为会自动支持本模组的大锅、盆装菜、木臼、大缸和烤架。**

中央厨房（下称 CCK）是一个面向农夫乐事及其附属的集成集合，不是给任意第三方方块使用的通用 API。它现有实现主要盯住农夫乐事的具体类：

- `CookingPotBlockEntity`
- `CuttingBoardBlockEntity`
- `SkilletBlockEntity`
- `AbstractStoveBlockEntity`
- 农夫乐事的 `FeastBlock` / `PieBlock`

本模组的大锅是自定义 `BigStoveBlock` / `BigPotBlockEntity`，盆装菜 `DdFeastBlock` 也不是农夫乐事的 `FeastBlock`，所以不会被 CCK 的现成动力臂或打包机逻辑识别。

分层次判断：

1. **标准农夫乐事配方**：本模组的 60 条 `farmersdelight:cooking` 配方和现有 `farmersdelight:cutting` 配方具备被 CCK 利用的条件（1.21.1 用打包机 + 动力臂；1.20.1 需要烈焰灶 + 烹饪指南）；但这不是大锅兼容。
2. **本模组自定义方块**：必须自己做 Create 的 `ArmInteractionPointType`、`UnpackingHandler` 或方块状态交互，不能靠 CCK 零代码接管。
3. **让 CCK 原生识别本模组**：需要给 CCK 增加独立集成（或修改 CCK），不建议作为本模组自己的前置方案。

**推荐方向：把 CCK 当作可选运行环境，本模组自己实现一层 Create 兼容；不要硬依赖 CCK，也不要把 CCK 的内部类当成稳定 API。**

| 1.21.1 | 分支 `1.21.1/6.0.0-dev`，HEAD `df9cc5c`，CCK `2.6.2b` | NeoForge `>=21.1.0`、Create `>=6.0.10`、Create Dragons Plus `>=1.11.9`、农夫乐事 `>=1.3.2` | 打包机负责把食材解包进农夫乐事烹饪锅的 `0..5` 槽；动力臂负责容器槽 `7` 和成品槽 `8` |
| 1.20.1 | 分支 `1.20.1/6.0.0-dev`，HEAD `7d04a04`，CCK `1.5.1` | Forge `>=47.4.10`、Create `>=6.0.8,<6.1.0` | 农夫乐事烹饪锅必须放在 CCK 的 `BlazeStoveBlockEntity` 上方，并由其 `CookingGuide` 指导动力臂投料；未发现同等的打包机食材解包处理 |

本模组当前两版的基线：

- 1.21.1：NeoForge `21.1.250`、Create `6.0.10`、农夫乐事 `1.3.4`，与 CCK 1.21.1 的版本范围相容；实际测试环境还需要补 Create Dragons Plus。
- 1.20.1：开发客户端实际运行 Forge `47.1.33`，低于 CCK 1.20.1 声明的 `>=47.4.10`。虽然本模组自己的 `mods.toml` 允许 `[47.1.0,48)`，但要在 1.20.1 实测 CCK，必须单独准备 Forge `47.4.10+` 的运行环境。

另：1.21.1 分支的 CCK 源码使用 `LGPL-3.0-or-later` 许可；1.20.1 分支的 `mods.toml` 写的是 MIT。实现时只调用公开 API、不复制 CCK 的具体实现，避免把两套许可证和本模组的 MIT 许可混在一起。

主要核对入口：

- CCK 1.21.1：`src/integration/farmersdelight/.../FDIntegration.java`、`CookingPotArmInteractionPoint.java`、`PortionableFoodArmInteractionPoint.java`、`CookingPotUnpackingHandler.java`、`CuttingBoardRecipeConverters.java`，以及 `common/integration/ModIntegration.java`。
- CCK 1.20.1：`content/logistics/block/mechanicalArm/CookingPotPoint.java`、`content/contraptions/blazeStove/BlazeStoveBlockEntity.java`、`content/contraptions/components/actor/HarvesterMovementBehaviourExtension.java`、`resources/META-INF/mods.toml`。
- 本模组：`block/BigPotItemHandler.java`、`block/BigPotCooking.java`、`block/BigPotBlockEntity.java`、`block/DdFeastBlock.java`、`block/MysteryStewPotBlock.java`。

## 为什么不能零代码接管

### 1. CCK 的集成是硬编码的

1.21.1 的 `ModIntegration` 是一个封闭枚举，列出农夫乐事、Brewin' and Chewin、Miner's Delight 等固定集成。没有公开的“第三方方块注册自己的 CCK 集成”注册表。

1.21.1 的 `FDIntegration` 只把农夫乐事烹饪锅的有效方块注册到打包机解包处理器：

```java
ModBlockEntityTypes.COOKING_POT.get()
        .getValidBlocks()
        .forEach(block -> UnpackingHandler.REGISTRY.register(block, new CookingPotUnpackingHandler()));
```

这不是“任意 `IItemHandler` 都能自动获得烹饪锅语义”的接口。

### 2. 动力臂只处理农夫乐事烹饪锅的固定槽位

1.21.1 的 `CookingPotArmInteractionPoint` 只做三件事：

- 往容器槽 `7` 放容器；
- 从成品槽 `8` 取成品；
- 其余食材槽依赖打包机解包。

它首先要求方块实体是 `CookingPotBlockEntity`。本模组的大锅不是这个类型。

1.20.1 的 `CookingPotPoint` 还额外要求：

- 下方是 CCK 的 `BlazeStoveBlockEntity`；
- 烈焰灶里放着 `CookingGuide`；
- 方块实体是 `CookingPotBlockEntity`。

本模组 2×2 的大锅既不是单格烹饪锅，也没有 CCK 的烈焰灶/烹饪指南语义。

### 3. 可分段食物只认农夫乐事类型

1.21.1 的 `PortionableFoodArmInteractionPoint.Type` 判断条件是：

```java
state.getBlock() instanceof FeastBlock || state.getBlock() instanceof PieBlock
```

本模组 `DdFeastBlock` 直接继承 `Block`，所以不在这个判断里。即使它的 `SERVINGS` 属性看起来相似，也不会被自动识别。

### 4. 本模组大锅的物品能力不是 CCK 期望的槽位模型

`BigPotItemHandler` 当前只有 1 个槽，且只负责“从上方投一个物品进去”，`extractItem()` 永远返回空。CCK 的打包机解包要求目标至少有 6 个可写槽（烹饪锅的 `0..5`），并在槽位上逐项匹配配方；1 个槽的处理器会在前置检查就被拒绝。

同时，`BigPotCooking#dropIn()` 当前拒绝带合成剩余物的物品，自动化调料基本只接受盐；瓶装酱油、醋、油和碗装大酱不会按 CCK 的打包机模型工作。锅盖也不是物品槽中的物品，而是 `Pot.LID` 方块状态加 `BigPotBlockEntity` 内部保存的栈，必须另做交互点。

### 5. 盆装菜有自己的取餐语义

`DdFeastBlock` 需要先拿碗，取餐后可能把方块换回普通大脸盆；盆装谜之炖菜还会从方块实体读取效果，生成不同内容的碗装谜之炖菜。这个动态 `servingStack(Level, BlockPos)` 不能直接套用 CCK 只依赖方块状态的 `FeastBlock` 逻辑。

## 可实施方案与难度

| 方案 | 难度 | 可行性 | 说明 |
|---|---:|---|---|
| 只在农夫乐事烹饪锅中使用 CCK | 低 | 高 | 本模组 60 条标准烹饪配方可直接利用；需要实测 1.21.1 打包机 + 动力臂、1.20.1 烈焰灶 + 烹饪指南 |
| 给大锅增加自定义动力臂交互点 | 中高 | 高 | 可复用 `BigPotCooking` 的投料/开煮入口；锅盖、投料和成品最好拆成明确的交互状态，不能只暴露现有 1 槽物品能力 |
| 给大锅增加打包机 `UnpackingHandler` | 高 | 中 | 需要按 `BigPotRecipe` 做整包匹配、精确数量校验、水量/容器检查、模拟执行和失败回滚；不是写一个 `IItemHandler` 适配器就能完成 |
| 给 `DdFeastBlock` 增加动力臂取餐 | 中 | 高 | 建议自定义 `ArmInteractionPointType`，按“放碗 → 取碗装菜 → 最后一份变空盆”实现；盆装谜之炖菜要保留方块实体效果 |
| 直接继承农夫乐事 `FeastBlock` 换取 CCK 自动识别 | 中高 | 有条件 | `DdFeastBlock` 的属性、放置、取餐和最后一份变空盆行为接近 FD，但谜之炖菜依赖方块实体，且会改变现有继承关系；需要完整回归，不能作为第一步 |
| 让大锅继承 `CookingPotBlockEntity` | 极高 | 低 | 会与 2×2 大灶、锅盖、水体、`BigPotRecipe` 和现有渲染/存档冲突；不建议 |
| 给 CCK 上游提交原生集成 | 高 | 有条件 | 需要给 CCK 增加集成枚举、源码集、构建依赖、两版不同的交互点和 GameTest；适合长期方案，不适合作为本模组的硬前置 |

## 推荐落地顺序

1. **先做零代码验证**：在 1.21.1 使用农夫乐事烹饪锅 + CCK 打包机/动力臂，确认本模组 60 条标准烹饪配方和切割配方能被正常自动化；在 1.20.1 使用 47.4.10+、Create 6.0.8 和 CCK 1.5.1 验证烈焰灶模型。
2. **本模组自己实现 Create 兼容层**：优先做 `BigPot` 的食材投入和锅盖交互，以及 `DdFeastBlock` 的取餐交互；CCK 不在时也应当能工作。
3. **再考虑打包机全流程**：只有在决定给大锅增加明确的内部输入/输出槽，或实现完整的 `BigPotRecipe` 事务式解包后，才做打包机自动投料。
4. **CCK 专用代码隔离**：如果确实要调用 CCK 的烈焰灶、烹饪指南或内部扩展，放在单独的 `compat/cck` 包，按 `create_central_kitchen` 是否加载做条件类加载；不要把这些类放进基础方块类。
5. **不把 CCK 加入硬依赖**：本模组仍以农夫乐事为必需前置，Create/CCK 均为可选兼容；这样不会让未安装 CCK 的玩家无法启动，也不会把 CCK 的开发分支 API 固定死。

## 风险清单

- CCK 1.21.1 当前是 `6.0.0-dev` 分支上的 `2.6.2b`，内部类和交互语义仍可能变化。
- 1.20.1 与 1.21.1 的 CCK 架构不同，不能共用一套适配实现；1.20.1 还没有与 1.21.1 对等的打包机食材解包路径。
- 1.20.1 的当前开发客户端是 Forge `47.1.33`，不能直接加载要求 `47.4.10+` 的 CCK；测试环境需要单独升级。
- 1.21.1 CCK 需要 Create Dragons Plus；当前测试环境如果没有该前置，CCK 不会正常加载。
- 大锅的 `full()` 目前只按全局最大食材/调料数量判断，不判断“再放一个后是否仍有配方可匹配”。如果做自动投料，必须先补防过量投料和目标配方预检，否则打包机/动力臂很容易把一锅菜投成谜之炖菜。
- 直接复用 CCK 的 `StatefulBlockArmInteractionPoint` 或其它实现会引入许可证和版本耦合问题；应以 Create 公开 API 为基础，CCK 只作为行为参考。
- 盆装菜的取餐需要碗，且最后一份会变成大脸盆；任何自动化都必须保持这个状态转换，不能只减 `SERVINGS`。

## 最终判断

**能做，但不是“给 CCK 加一个适配器”那么简单。**

如果目标只是“本模组的标准农夫乐事配方可以用 CCK 自动化”，成本低，现有配方已经具备条件；如果目标是“CCK 的动力臂/打包机完整操作本模组的大锅和盆装菜”，则属于本模组自己实现一套 Create 兼容层的中高成本工作，且必须分别处理 1.21.1 的打包机模型和 1.20.1 的烈焰灶模型。

建议先把范围收敛为：**CCK 作为可选环境，本模组自己做 Create 动力臂兼容；先覆盖大锅投料/锅盖和盆装菜取餐，不先做打包机全流程，也不修改 CCK 核心。**
