## 三、工具链结论（重要，别重复踩坑）

| 方案 | 结论 |
| --- | --- |

| **NeoGradle 7.1.x（`net.neoforged.gradle.userdev` 7.1.39）** | ✅ 在 Gradle 9.2 上正常工作，MC 1.20.4 反编译/重编译全流程实测通过（`<探针工程>`）。7.1 线删掉了 mixin 插件 → mixin 配置改用 jar 清单 `MixinConfigs` |

选型：**NeoGradle `net.neoforged.gradle.userdev` 7.1.39 + NeoForge 20.4.189 + Gradle 9.2（保持工程现状）**。

### 踩坑：JST 工具要 Java 21

NeoGradle 7.1 的源码转换任务（`neoFormTransformSource` 等）跑的是
`net.neoforged.jst:jst-cli-bundle:2.0.11`，它是 **Java 21** 编译的 class（class file 65.0），
而 1.20.4 的版本清单只声明 Java 17，NeoGradle 会给这些任务发 JDK 17 →
`UnsupportedClassVersionError: net/neoforged/jst/cli/Main has been compiled by a more recent version ...`。

解决：只把这类"工具"任务的运行时提到 21（编译产物仍是 release 17），已写进 `build.gradle`：

```groovy
tasks.withType(net.neoforged.gradle.common.runtime.tasks.JavaSourceTransformer).configureEach {
    javaVersion.set(JavaLanguageVersion.of(21))
}
```

### 已经改完的移植点（按主题）

| 主题 | 1.20.4 的做法 |
| --- | --- |
| 方块右键：`ItemInteractionResult` → `InteractionResult` | 1.20.4 只有 `Block#use(...)` 返回 `InteractionResult`；1.20.5+ 才是 `useItemOn(...)` + `ItemInteractionResult`。逐个用 `//? if <1.20.5` 分支（如 `DdCropBlock`、`CornStalkBlock`、`SkewerBlock`、`Vat`…） |
| `ResourceLocation.parse(...)` | 1.20.4 用 `new ResourceLocation(...)` |
| `HolderLookup` / 注册表访问 | 世界生成按 1.20.4 的 `Registries` / `RegistryOps` 写法分支 |
| `DataComponents`（食物组件等） | 新增 `DdStacks.isEdible(stack)`：<1.20.5 走 `stack.isEdible()`，≥1.20.5 查 `DataComponents.FOOD`；`DdConsumableItem` / `DishBlockItem` 同理分支 |
| 药水效果 Holder | `DdEffects` 在 <1.20.5 需要显式 `(Holder<MobEffect>) holder` 强转 |
| NBT 工具 | `DdNbt.saveItem` 返回类型改成 `net.minecraft.nbt.Tag`（1.20.4 里 `ItemStack#save` 的返回类型是 `Tag` 不是 `CompoundTag`） |
| 事件总线 | `net.neoforged.neoforge.event.TickEvent` 与 `fml.common.Mod.EventBusSubscriber` 在 1.20.4 不存在 → 用 `/*...*/` 包进 <1.20.5 分支 |
| `getUpdateTag` | 1.20.4 没有 `HolderLookup.Provider` 版本 → `GrillBlockEntity` 按其签名分支（手写 `new CompoundTag()` + `writeToTag`） |
| 渲染层（`GrillCampfireRenderer` / `GrillRackGeometry` / `VatRenderer`） | 1.20.4 是老式 `VertexConsumer` 链：`vc.vertex(pose, x, y, z).color(...).uv(...).overlayCoords(...).uv2(...).normal(...).endVertex()`，1.20.6+ 才是 `addVertex(...).setColor(...)` |
| JEI 17.x（1.20.4 是 JEI 17，1.21.1 是 19+） | `GrillRecipeCategory` / `VatRecipeCategory` 手绘背景：17.x 没有 `getBackground` / `withSlotBackground`，改成 `draw(...)` 自己画格子与箭头 |
| 作物 / GameTest | 作物生长与收获走的 hook 按版本分流；`gametest/**` 里的 `mockPlayer` 等助手按 1.20.4 的 `GameTestHelper` API 改写 |
| 矿物词典 | `ModTags.item()` 按版本分流（<1.20.5 走 `forge:` + 路径改名表，≥1.20.5 走 `c:`），见第六节 |
| 标签里的 create 条目 | 1.20.4 没有 create，转换脚本把这类条目改成 `required: false`（详见第九节） |

> 注：`BLOCKS.registerBlock(id, factory, props)` 在 NeoForge 20.4 上也有，这批注册代码不需要分支。

## 八、机械动力（Create）到底有没有 1.20.4？—— 查证记录

结论：**Create 官方根本没有 1.20.2 ~ 1.20.6 的任何版本**。不是「我们没找到 1.20.1 的仓库」，
也不是「1.20.1 的版本差一点点」，而是作者在 1.20 这一代只做 1.20.1，之后直接跳到 1.21.1。

2026-10-08 实查证据：

- Modrinth API `https://api.modrinth.com/v2/project/LNytGWDc`（Create 的项目 id）返回的 `game_versions`
  只有四个：**1.18.2、1.19.2、1.20.1、1.21.1**。
- 同一接口按版本过滤：
  - `?game_versions=["1.20.4"]` → **0 个版本**；
  - `?game_versions=["1.20.1"]` → **17 个版本**（最新 `mc1.20.1-6.0.8`，loader 同时挂 forge + neoforge）；
  - `1.21.1` → 11 个版本。
- 本地 clone 的 Create 源码仓库 `<Create 源码 clone>` 只有三个远端分支：
  `origin/mc1.20.1/dev`、`origin/mc1.20.1/0.5.1`、`origin/mc1.21.1/dev` —— **没有 1.20.4 分支**，也没有对应 tag。

为什么 1.20.1 的 jar 不能直接拿到 1.20.4 上：

- MC 1.20.2 起把配方/注册表/数据组件那一整套内部 API 大改（`ItemStack` 写 NBT、`ResourceLocation` 构造、
  方块右键返回值、`ItemInteractionResult` 等，本工程自己就因为这些改了 134 处），
  Create 编译时依赖的中介名/Forge 47.x API 在 1.20.4 上对不上，属于**跨小版本硬不兼容**。
- Create 的 1.21.1 版本又是跟着 NeoForge 21.x 的 flywheel/ponder 重写的，也不是 1.20.4 的代码。

因此在 1.20.4 这个节点上，与机械动力有关的一切只能按版本排除：

| 内容 | 处理 |
| --- | --- |
| `compat/create/ModFanProcessingTypes.java`（风扇处理类型） | 整文件进 <1.20.5 排除分支 |
| 风干 JEI 分类 `compat/jei/DryingRecipeCategory` 等 | 同上，1.20.4 不注册 |
| 大缸接 Create 管道 / 黄铜相关联动 | 同上 |
| 47 个 `create:` 配方（`milling` / `mixing` / `filling` / `emptying` / `compacting` / `sequenced_assembly`） | 数据转换脚本整组丢弃 |
| 进度 `pump_seasoning.json`（图标是 `create:mechanical_pump`） | 数据转换脚本丢弃 |
| `forge:plates/brass` / `forge:plates/iron` 标签里的 `create:*_sheet` | 条目改成 `required: false`（留着标签，别家模组塞黄铜板进来还能用） |

## 九、1.20.4 数据包转换（`gradle/legacy-data-port.groovy`）

1.21.1 的 `data/**` 在 1.20.4 上大部分读不出来（目录名、ItemStack 字段名、标签命名空间都变了），
所以工程不再维护两份数据文件，而是在 `:1.20.4:processResources` 的 `doLast` 里**就地转换**
`versions/1.20.4/build/resources/main/data/**`。

`build.gradle`（1.20.x 分支）里的挂法：

```groovy
apply from: "${rootDir}/gradle/legacy-data-port.groovy"
def legacyResourcesOut = sourceSets.main.output.resourcesDir
tasks.named('processResources', ProcessResources).configure { task ->
    task.inputs.file("${rootDir}/gradle/legacy-data-port.groovy")   // 脚本改了要重跑
    task.doLast { portLegacyDataTree(legacyResourcesOut) }
}
```

转换规则（脚本头部注释里有同样一份）：

1. **目录改名**：`advancement→advancements`、`loot_table→loot_tables`、`recipe→recipes`、`structure→structures`；
   标签子目录 `block/item/entity_type/fluid/game_event` 改复数。
2. **JSON 结构**：配方/进度里 1.21 写 `"id"` 的 ItemStack，1.20.4 写 `"item"`。
3. **标签命名空间**：`c:` → `forge:`，并按 `legacyTagPathRenames` 改路径：
   `foods/dough/wheat→dough/wheat`、`foods/raw_fish→raw_fishes`、`foods/bread→bread`、
   `tools/knife→tools/knives`、`foods/raw_beef/chicken/mutton/pork` 同名等。
   **这张表必须和 `ModTags#legacyPath`（<1.20.5 分支）保持一致。**
4. **丢弃**：`create` 专属配方目录整组 + `pump_seasoning.json`。
5. **条件/原料类型**：`neoforge:can_item_perform_ability` → `neoforge:can_tool_perform_action`（字段 `ability` → `action`）；
   `neoforge:components` 原料 → 普通物品原料（1.20.4 没有数据组件）。
6. **农夫乐事切菜板**：1.20.4 的 `result` 直接是 ItemStack（把 1.21 的 `{item:{id,count}}` 展平），
   `tool` 只收单个原料（取数组里带 `tag` 的那个）。
7. **标签条目可选化**：指向 1.20.4 上不存在的模组（目前是 `create`）的标签条目改写成
   `{"id": "...", "required": false}`。
   这一条是必要的：1.20.4 的 `TagEntry` 默认 `required=true`，缺一个引用就会让
   `TagLoader#build` 返回 left → 只打 error 日志、**整条标签不注册**
   （原先 `forge:plates/brass` 只有 `create:brass_sheet` 一条，整个标签会消失，连带 `brass_bowl` 配方出问题）。
8. **物品谓词**：1.21 把标签并进了 `HolderSet`，写 `"items": "#tag"`；1.20.4 的 `ItemPredicate`
   还是两个字段（`tag` 不带 `#`、`items` 必须是数组），所以 `"items": "#x"` → `"tag": "x"`、
   `"items": "x"` → `"items": ["x"]`。
9. **战利品上下文实体名**：1.21 的 `"entity": "attacker"` 在 1.20.4 叫 `killer`
   （`direct_attacker`→`direct_killer`、`attacking_player`→`killer_player`）。

> 第 8、9 条都是实机跑服务端才暴露的：`pig_offal` 掉落修改器在修之前会被整条跳过，
> 而且日志里的报错信息是 `Not a json array: {...}`——那是 `LootItemConditions.CODEC`
> 回退到「内联 all_of 数组」分支时打出来的假线索，真正的原因在 `entity_properties`
> 条件内部（`EntityTarget` 名字对不上），排查时别被它带偏。

其它细节：JSON 用 `JsonOutput.prettyPrint`（4 空格）+ 末尾换行重写；
Groovy `JsonOutput` 会把中文转义成 `\uXXXX`，脚本里有 `legacyUnescapeUnicode` 还原回来。
