# 切割机械动力后的东北小院结构互斥评估

日期：2026-11-04

范围：只评估“装了机械动力就加载结构 A，没装就加载结构 B，两者互斥”是否可行、推荐怎么做、风险在哪里。本轮不修改源码、不构建、不启动客户端。

## 结论

可以做到。两条路都可行：

- **单结构 ID + 双模板池**：结构 JSON 不变，在 codec 里按 `ModList` 选模板组；
- **两套完整结构 + 两套结构集**：两套结构 JSON 各放一个完整 NBT，两套结构集各自引用自己的结构，双方都用条件加载。

如果已经决定“一个结构只放一个完整 NBT”，推荐第二条路，也就是两套完整结构加两套结构集。它的代码改动反而更少，主要成本在结构文件、条件字段和存档兼容。

单结构 ID 方案仍然保留为备选：在一套结构配置里增加两组互斥模板：

- `templates_with_create`：检测到机械动力时使用；
- `templates_without_create`：没有机械动力时使用；
- 原来的 `templates` 继续作为旧数据包的兼容回退。

结构对象创建时用 `ModList` 只选其中一组，之后整片小院群落都使用这一组模板。这样两个模板池不会混用，结构 ID、结构集、群系标签、间距、盐值和村庄避让规则都不变。

两种方案的关键差别：

| 项目 | 单结构 ID + 双模板池 | 两套完整结构 + 两套结构集 |
| --- | --- | --- |
| Java 代码 | 需要增加字段和 `ModList` 分支 | 当前 `templates` 足够，通常不改 Java |
| 结构 ID | 一个 | 两个 |
| 结构集 | 一个 | 两个，各自带互斥条件 |
| 旧存档结构 ID | 原样保留 | 原 ID 保留为兼容入口，新无 Create 结构用新 ID |
| 放置网格 | 不变 | 只要 spacing / separation / salt 相同就不变 |
| 主要风险 | 模板池选错、代码分支 | 条件加载、结构集引用、旧存档兼容 |

## 当前实现事实

- 结构定义：`src/main/resources/data/northeast_china_delight/worldgen/structure/northeast_yard.json`
- 放置结构集：`src/main/resources/data/northeast_china_delight/worldgen/structure_set/northeast_yards.json`
- 结构代码：`src/main/java/com/gunmu/northeast_china_delight/worldgen/NortheastCourtyardStructure.java`
- 结构集里只有一个 `northeast_china_delight:northeast_yard`，`spacing=64`、`separation=24`、`salt=20260930`。
- 结构 JSON 当前启用三套模板：`northeast_yard_garden`、`northeast_yard_compound`、`northeast_yard_livestock`。
- `NortheastCourtyardStructure` 的 codec 已有 `templates` 字符串列表字段；构造器保存该列表，`pickTemplate()` 在列表里随机取一个。

因此，模板选择本身已经是数据驱动的，增加“有 Create / 无 Create”两套列表属于低侵入改造。

## 推荐实现

### 1. 结构 JSON

保留旧字段，新增两组：

```json
{
  "templates": [
    "northeast_china_delight:northeast_yard_garden",
    "northeast_china_delight:northeast_yard_compound",
    "northeast_china_delight:northeast_yard_livestock"
  ],
  "templates_with_create": [
    "northeast_china_delight:northeast_yard_garden",
    "northeast_china_delight:northeast_yard_compound",
    "northeast_china_delight:northeast_yard_livestock"
  ],
  "templates_without_create": [
    "northeast_china_delight:northeast_yard_garden_no_create",
    "northeast_china_delight:northeast_yard_compound_no_create",
    "northeast_china_delight:northeast_yard_livestock_no_create"
  ]
}
```

旧数据包只写 `templates` 时维持旧行为；新数据包可以只覆盖其中一组。无 Create 组必须是非空的“纯原版方块模板”，不能回退到含 `create:*` 的旧模板。

### 2. Java 选择点

在结构 codec 中增加两个可选列表字段，在构造器里做一次二选一：

```java
boolean hasCreate = ModCompat.isCreateLoaded();
List<String> selected = hasCreate ? templatesWithCreate : templatesWithoutCreate;
this.templates = selected.isEmpty() ? legacyTemplates : selected;
```

这里的“二选一”应当在结构对象构造时完成，而不是每座院子重新掷骰子。否则同一片小院群落可能一半有 Create 装饰、一半没有，不是真正的互斥 profile。

双版本判断 API 不同，建议用 Stonecutter 包一层：

- 1.20.1：`net.minecraftforge.fml.ModList.get().isLoaded("create")`
- 1.21.1：`net.neoforged.fml.ModList.get().isLoaded("create")`

项目里已经有同样的 Stonecutter 版本分支写法，例如 `NortheastChinaDelight.java` 对 JEI 的检测，因此接入成本低。

### 3. 如果两套结构连群系、间距都要不同

推荐把“完整 profile”放进同一个结构 codec，例如 `profile_with_create` / `profile_without_create`，每个 profile 包含自己的模板、群系、间距等字段。这样结构集仍然只引用一个结构，不会出现结构集引用缺失 holder 的问题。

如果坚持拆成两个结构 ID 和两个结构集，则需要：

- 两套 `worldgen/structure/*.json`；
- 两套 `worldgen/structure_set/*.json`；
- 条件加载或运行时跳过其中一套；
- 保证结构集不会引用未注册的结构 holder。

这条路的兼容和维护成本明显更高，不推荐作为第一版。

## 两套完整结构 + 条件加载的正确做法

已核对两条加载链：1.20.1 Forge 在 `RegistryDataLoader.loadElement` 解析前调用 `ICondition.shouldRegisterEntry`；1.21.1 NeoForge 则用 `ConditionalOps` 包住注册表条目解码。因此 `worldgen/structure` 和 `worldgen/structure_set` 都可以在文件顶层写条件，条件不满足时整个条目不会注册。

1.21.1 的写法：

```json
{
  "neoforge:conditions": [
    {
      "type": "neoforge:mod_loaded",
      "modid": "create"
    }
  ]
}
```

无 Create 使用取反：

```json
{
  "neoforge:conditions": [
    {
      "type": "neoforge:not",
      "value": {
        "type": "neoforge:mod_loaded",
        "modid": "create"
      }
    }
  ]
}
```

结构文件和结构集都要成对加同一个条件。只给结构加条件、不给结构集加条件，仍然可能让结构集引用到缺失的结构 holder；只给结构集加条件、不给结构加条件，结构虽然注册但不会生成，通常无害，但条件语义不完整。

推荐文件布局：

- `northeast_yard.json`：旧 ID，保留为 Create 版完整结构；
- `northeast_yard_no_create.json`：新 ID，无 Create 版完整结构；
- `northeast_yards.json`：旧结构集，加 `mod_loaded create` 条件；
- `northeast_yards_no_create.json`：新结构集，加 `not(mod_loaded create)` 条件。

这样旧存档里已经存在的 `northeast_yard` 结构引用仍然能解析；无 Create 的新区域只生成 `northeast_yard_no_create`，两套结构集不会同时生效。

1.20.1 的 `legacy-data-port.gradle` 会把 1.21.1 的 `neoforge:conditions` 自动改成 `forge:conditions`，并把 `neoforge:mod_loaded` 改成 `forge:mod_loaded`。如果使用 `neoforge:not`，转换表目前还没有这一项，需要补上 `neoforge:not -> forge:not`；同理建议把 `and`、`or` 一并补齐，避免以后写复杂条件时 1.20.1 留下错误的命名空间。

这条路的实际难度是**低到中**：不需要改结构 codec，结构 JSON 的 `templates` 只放一个完整 NBT 即可；需要新增条件字段、成对结构集、无 Create NBT，并做两版本加载验证。

## 现有模板不能直接当作“无 Create 版本”

本轮检查了当前启用的三套 NBT，均包含 `create:*` 方块：

- `northeast_yard_garden`：`create:cogwheel`、`create:millstone`、`create:water_wheel`、`create:industrial_iron_block`、copycat 系列等；
- `northeast_yard_compound`：`create:gearbox`、`create:hand_crank`、`create:hose_pulley`、`create:speedometer`、copycat 系列等；
- `northeast_yard_livestock`：`create:copycat*`、`create:polished_cut_calcite*`、`create:red_table_cloth`、`create:stressometer` 等。

没有机械动力时，这些方块不会自动变成原版方块，也不会自动删除。结构模板加载时可能出现缺失方块、空洞、调色板解析告警，甚至区块生成异常。因此：

- 必须另做三套 `*_no_create.nbt`；
- 把石磨、齿轮、风车、copycat、座椅、桌子、窗框等替换为形似的原版方块或直接删掉；
- 保留旧 NBT 文件，不要删除。旧存档中已经生成的结构 piece 仍引用旧的模板 ID。

这部分内容制作才是本任务的主要工作量，代码分支不是。

## 互斥语义与存档行为

- 选择依据是**服务器当前加载的模组列表**；单人游戏由集成服务器决定。
- 已生成区块不会因为后来装/卸 Create 而重写；只有新生成区块使用新分支。
- 同一个种子在“有 Create”和“无 Create”环境下，院落内容可以不同；如果结构 ID 和结构集不变，放置网格和盐值仍保持一致。
- 旧存档必须保留旧模板 NBT；新分支只新增模板，不覆盖旧 ID。
- 服务端和客户端应保持同一套 Create 状态。服务端有 Create、客户端没有时，即使结构分支选中了 Create 版，客户端也无法正确显示这些方块。

## 这还不等于“机械动力已切割”

结构分支只解决小院模板。真正让模组在无 Create 环境下启动，还需要独立处理：

- `src/main/templates/META-INF/neoforge.mods.toml` 与 `src/main/templates-forge/META-INF/mods.toml` 当前都把 Create 声明为必需依赖；
- `NortheastChinaDelight.java` 无条件调用 `ModFanProcessingTypes.register(...)`，该类直接引用 Create API；
- JEI 风干分类 `DryingRecipeCategory` 直接 import Create/Catnip 类；
- 数据包中大量 `create:*` 配方类型需要确认缺失 Create 时会被安全跳过；
- 大缸与 Create 流体/管道相关的运行时代码要隔离到可选 compat 层。

这些应当作为“切割机械动力”的第二阶段单独做，不要和结构模板分支混在同一个改动里。

## 工作量与风险

| 方案 | 代码量 | 主要内容 | 风险 |
| --- | --- | --- | --- |
| 单结构 ID + 双模板池 | 低 | codec 加两组字段、`ModList` 分支、结构 JSON | 低；旧数据包可兼容 |
| 单结构 ID + 双完整 profile | 中 | 模板、群系、间距等都可分支 | 中；codec 和校验更复杂 |
| 两个结构 ID + 条件加载 | 低到中 | 双结构、双结构集、条件注册表 | 中；需保证结构和结构集成对条件化，并验证旧存档 |
| 真正移除 Create 前置 | 高 | 元数据、compat 类隔离、配方/方块缺失测试 | 高；应独立立项 |

只做结构模板互斥时，代码改造预计半天以内；三套无 Create NBT 的制作和验收另计。

## 建议验收

1. 有 Create：生成小院，确认只出现 `templates_with_create` 中的模板。
2. 无 Create：生成小院，确认只出现 `templates_without_create` 中的模板，日志无缺失调色板 / 方块错误。
3. 旧数据包只写 `templates`：行为与升级前一致。
4. 同一存档切换 Create 状态：已生成区块不变化，新生成区块按当前分支选择。
5. 专用服务器：以服务端模组列表为准，客户端模组集合一致时正常进入。

## 最终建议

如果已经抛弃模板池，直接做“两套完整结构 + 两套结构集”即可。代码基本不动，重点是把无 Create NBT、结构和结构集的条件、旧存档兼容和双版本加载测试做完整。等结构部分稳定后，再单独推进元数据和 Java compat 层的 Create 可选化。
