# 未来版本适配准备

> 适用范围：当前 `3.1.0` 代码线（1.21.1 / 1.20.1）。本文不是功能补齐清单，而是为后续 Minecraft / NeoForge / Forge 版本迁移预留的低风险准备工作。
> 原则：先冻结数据契约和语义，再换 API；不把尚未定稿的玩法写死进存档格式。

## 1. 当前可复用的基础

- Stonecutter 双节点已经承担源码级版本差异；新增版本敏感代码必须继续走整行条件编译。
- 数据包路径即稳定配方 ID；大缸、烤架、风干、舂捣都走原版 `RecipeManager`，不使用硬编码配方表。
- `DdIds`、`DdStacks`、`DdNbt` 已经隔离了一批跨版本资源位置、物品堆和 NBT 差异。
- 盆装菜、木臼、木槌的自定义模型与渲染已有独立资源路径，版本升级时适合先跑模型/贴图门禁。
- JEI、Jade、Create、ALI 都通过 `compat` 包隔离，版本升级时应先确认依赖是否支持目标版本，再改主代码。

## 2. 现在就应该维持的契约

1. **配方字段不随意改名**：`input`、`tool`、`pound_times`、`result`、`priority`、`disabled`、`stage_models`、`transition` 至少保留到下一个大版本；语义变更用新字段或新版本号承接。
2. **配方 ID 不随实现变化**：文件名/路径就是 ID；改实现时保持路径不变，避免整合包覆盖失效。
3. **存档字段保持可读**：木臼继续保存 `PoundRecipe` 与 `PoundProgress`；新增字段必须允许旧存档缺省。
4. **逻辑阶段与视觉模型分离**：木臼的 `STATE` 继续表示逻辑阶段；不要为了换模型把阶段编号重新分配。
5. **资源路径保持稳定**：`wooden_mortar_N`、盆装菜 `servingsN`、大缸/烤架模型路径不要在版本迁移时批量改名；需要换模型时优先替换文件内容。

## 3. 推荐的低风险准备

### P0：下次改配方序列化器之前

- 给自定义配方 `config` 增加可选 `schema_version`（默认 1）。旧配方不写也能加载；加载器遇到高于当前支持的版本时给出明确错误，而不是静默误解字段。
- 把各版本的 `Ingredient` / `RecipeInput` / `HolderLookup` / `FriendlyByteBuf` 差异集中到少量适配方法，避免每个配方序列化器各自写一套条件编译。
- 为舂捣、大缸、烤架、风干各留一份最小 JSON 夹具，迁移版本后先跑解析测试，再跑玩法测试。

### P1：舂捣真正补齐之前

- 明确 `stage_models` 的最终语义：要么实现自定义模型渲染并保留这个字段，要么把它改名为 `stage_count`，另加新字段承接模型列表。不要在未决定前继续往这个字段塞更多含义。
- 把 `Transition.CONDITIONAL` 保持为显式未实现状态；加载时可以对使用 `conditional` 的配方打印一次警告，避免整合包误以为它已生效。
- 木臼解析不到配方时增加恢复路径：至少允许挖掘/清空，最好按可配置策略返还或丢弃已投入物，避免删配方后永久卡死。

### P2：跨 Minecraft 大版本升级时

- 先建立“版本能力矩阵”：Minecraft、加载器、Java、JEI、Jade、Create、Farmer's Delight、ALI 是否可用，再决定节点是否保留。
- 先升级资源与模型门禁，再升级 Java：模型 JSON 的 schema、物品模型定义、方块状态格式通常比业务代码更早暴露问题。
- 先跑 `processResources`、模型旋转检查、配方解析夹具，再跑 GameTest / 客户端；配方序列化错误应在无界面阶段暴露。
- 不在迁移提交里顺手改玩法数值。模型、配方、兼容层分开提交，便于定位回归。

## 4. 不建议现在做的事

- 不要为了未来版本提前引入未验证的 API 抽象层；只隔离当前已经出现两次以上的版本差异。
- 不要在没有渲染方案前让 `stage_models` 接受“任意模型 ID”，否则数据包会写出看起来合法、实际不生效的配置。
- 不要把 `pound_times`、蓄力阈值、工具类型写进方块状态；这些属于配方/规则，不属于视觉状态。
- 不要重命名现有配方路径或存档 key。需要迁移时增加兼容读取分支。

- [ ] 现有配方 JSON 夹具全部能解析。
- [ ] 大缸、烤架、风干、舂捣的 JEI 页面仍能打开。
- [ ] 木臼旧存档能读取；删除/禁用配方不会卡死。
- [ ] 模型旋转、缺失贴图、非法元素检查通过。

## 6. 现有数据包新增舂捣配方（3.1.0 扩展）

新增文件：`data/<namespace>/recipe/pounding/<id>.json`，顶层为 `"type": "northeast_china_delight:pounding"`，规则写在 `config`。

新格式示例：

```json
{
  "type": "northeast_china_delight:pounding",
  "config": {
    "inputs": [
      {
        "ingredient": { "item": "farmersdelight:cooked_rice" },
        "count": 2,
        "return_container": { "item": "minecraft:bowl" }
      },
      { "ingredient": { "tag": "c:foods/sugar" }, "count": 1 }
    ],
    "tool": { "item": "northeast_china_delight:wooden_mallet" },
    "pound_times": 4,
    "charge_threshold": 0.9,
    "stage_models": [
      "northeast_china_delight:block/wooden_mortar_1",
      "northeast_china_delight:block/wooden_mortar_2"
    ],
    "results": [
      { "item": "northeast_china_delight:pounded_rice_cake", "count": 2 },
      { "item": "minecraft:sugar", "min_count": 1, "max_count": 3, "chance": 0.25, "byproduct": true }
    ],
    "result_mb": 50,
    "result_container": { "item": "minecraft:glass_bottle" },
    "random_results": [
      {
        "id": "bonus",
        "chance": 0.5,
        "entries": [
          { "item": "minecraft:sugar", "weight": 3, "count": 1 },
          { "item": "minecraft:egg", "weight": 1, "min_count": 1, "max_count": 2 }
        ]
      }
    ],
    "transition": "sequential"
  }
}
```

**可以做到**

- 多输入、多数量：`inputs` 数组，每项有 `ingredient` + `count`；`ingredient` 支持物品、标签和多选。一次右键最多投入该槽还缺的数量，可分批右键。
- 每项输入独立返还容器：`return_container` 可写在每个 `inputs` 项里；每实际消耗一份就返还一次。旧的顶层 `return_container` 仍然可用。
- 多产物 / 副产物：`results` 数组；`byproduct` 只影响 JEI 标记，实际发奖与普通产物相同。
- 可选取货容器 / 计量产物：`result_container` 指定取出成品时必须手持并消耗的容器；再写 `result_mb` 时，成品必须是唯一、必出、数量 1 的瓶装调料，且 `result_mb` 不超过瓶子的 `250 mB`。JEI 会把容器显示在箭头下方并标「容器」，产物下方直接显示每次的 `mB` 数。它是「取成品容器」，不要和输入项里的 `return_container` 混用。
- 随机种类：`results` 里的每项仍按 `chance` 独立掷骰；需要“只出一个”的互斥结果时用 `random_results` 权重池（同一个池只选中一项，池可整体设 `chance`）。
- 随机数量：固定写 `count`；随机写 `min_count` / `max_count`（闭区间）。
- 每配方蓄力阈值：`charge_threshold`（0..1，默认 0.9）。判定在服务端解析到配方后执行。
- 自定义加工外观：`stage_models` 写 1~4 个方块模型 id，state 1..N 与成品 state N+1 会按列表逐个渲染。模型文件放在资源包 `assets/<namespace>/models/block/*.json`；客户端会登记资源包内全部方块模型。
- 顺序 / 随机外观切换：`transition` 用 `sequential` 或 `random`。
- 配方管理：路径即 ID；可用 `priority` 处理重叠输入，用 `disabled` 停用。
- 兼容旧格式：只有 `input` / `return_container` / `result` 的旧配方无需修改；旧产物按固定 1 项、必出处理。

**仍然不能做到**

- 不能按输入物品 NBT / 组件内容做额外条件；匹配仍走 Ingredient。
- 不能给不同阶段指定不同工具、不同敲击次数或概率权重。
- 不能使用 `conditional` 做真正的条件切换；它目前不切模型。
- 不能给同一 `random_results` 池内的条目分别设置独立概率；池只有一个整体 `chance`，条目只按 `weight` 竞争。
- 不能自定义音效、粒子或 JEI 槽位排版；但 `inputs`、`results`、`result_container` 与 `result_mb` 会自动映射到现有 JEI 布局。

**实现约定**

- 所有输入满足前，木臼保持 state 0；满足后进入 state 1。部分投入时不能放槌，也不能挖掉。
- 成品在最后一次有效敲击时统一掷骰并快照到方块实体；之后 `/reload` 或重启不会重掷。
- 配方在加工中被删除 / 禁用时，空手右键会优先发出已快照产物；没有快照则退还已投入输入，不会永久卡死。
- JEI 逐项显示输入数量和全部产物；随机产物 tooltip 显示概率、数量范围、副产物，非默认蓄力阈值显示在次数下方。
