# 区域作物启用与售卖实施评估（2026-11-11）

> 状态：评估稿，未改功能代码。
> 适用范围：CRCI（中国烹饪食材）及以它为前置的地区乐事。
> 目标：由各地区的乐事决定“哪些作物存在、哪些可以进村庄农田、哪些可以出现在交易中”，而不是由 CRCI 或东北乐事写死。未安装地区乐事的内容必须不可见、不可生成、不可交易，只能由 `/give` 等指令取得。

> 2026-11-11 用户确认：
> - 所有食材都放进 CRCI，包括只有某个地区才会用到、别的地区完全没有的食材；地区乐事通过启用表决定它们是否进入游戏可见范围和投放。
> - 地区专属内容指菜肴、建材、结构这类内容，不能被其他地区启用。干辣椒这类食材属于 CRCI 的通用内容，只是由相应地区启用。
> - 大脸盆之类的容器/工具属于 CRCI 基础内容，不进入“自动售卖作物和食材”的全局交易池。
> - 农田的每个气候总替换率由 CRCI 固定，地区只决定作物列表和池内权重。
> - 配置只控制自然生成、村箱战利品和村民交易等获取途径，不控制 CRCI 物品的合成能力；启动/重载时重新计算。
> - 副食店和副食商在 CRCI，每个村庄最多一个副食店。
> - 旧存档物品保留，不自动删除；没有地区启用时在物品信息里提示“没有模组用到这个物品”，地区重新启用后提示消失。
> - 用 `/give` 取得的禁用物品仍可正常参与配方和机器加工；地区乐事只控制自然生成、战利品和村民交易等获取途径，不控制 CRCI 物品的合成能力。
> - 交易采用“CRCI 默认交易 + 地区覆盖/注入”：启用 CRCI 食材时自动获得默认买卖项，地区可覆盖价格/等级，也可注入自己的菜肴、建材等专属交易。
> - 默认交易池覆盖五类食物相关职业：农民、流浪商人、副食商、屠夫、渔夫；每样食材由 CRCI 指定适合的职业和等级，不是五个职业都卖同一样东西。
> - 卸载地区模组时，地区独有内容由游戏正常删除；留在存档里的 CRCI 食材保留并显示无模组使用提示。
> - 只安装 CRCI、没有任何地区乐事时，不生成副食店和副食商。

## 一、结论

可行，而且不需要为每个地区复制一套 Java 生成器或交易类。需要做的是把现在混在一起的三件事拆开：

1. **内容归属**：食材统一归 CRCI；菜肴、建材、结构等专属内容归各自地区，并判断其模组是否安装。
2. **内容启用**：该地区是否允许这项物品参与游戏内可见内容。
3. **使用位置**：即使启用了，是否允许放进某个气候的村庄农田、某个职业的某级交易、箱子战利品或野生生成。

只做一张“允许作物名单”不够。它无法表达“大豆启用，但不进沙漠农田”“辣椒启用，但只在副食商 3 级出售”“西南乐事没安装时，干辣椒连 JEI 都不能出现”。因此需要地区档案、统一的可用性服务，以及农田和交易两个数据驱动的投放层。

建议先做一个端到端样板（大豆或玉米），确认数据格式、客户端同步和旧行为不回退，再迁移全部 16 种作物。

## 二、现状审计

### 2.1 农田

- `VillageFarmCropRuleTest` 只拿到 `BlockState` 和 `RandomSource`，没有群系、坐标或结构上下文。
- 结果是一个作物一条规则，每条规则自己判断 `isVillageFarmCropAllowed`。关闭一部分作物后，其他作物的概率不会重新归一化，替换比例会整体变低。
- 当前由东北乐事整文件覆盖 5 个原版 `farm_*` 处理器列表，另有 1 个 `farm_taiga_small`；其他模组若也整文件覆盖，会互相顶掉。
- 作物规则还写死了“输入方块 = 小麦”“输出 = 某个完整生长方块状态”。这些都不能由地区乐事自行声明。

### 2.2 售卖与掉落

- `ModFarmerTrades`、`ModWandererTrades`、`SideDishMerchantTrades` 全部是 Java 硬编码，没有所属地区字段。
- `SideDishMerchantTradeMixin` 直接假定“大师级必定有黄桃罐头”，同样是东北乐事专属逻辑。
- `VillageSeedsLootModifier`、`StructureSeedsLootModifier` 的候选表是静态数组；`ChestLootConfigModifier` 只认东北命名空间。
- `NortheastChinaConfig.isChestLootItemAllowed()` 对非东北命名空间一律返回 `true`。CRCI 接管后，这会把未启用地区的 CRCI 物品放进箱子，必须改成按归属检查。
- 交易在 `VillagerTradesEvent` / `WandererTradesEvent` 触发时一次性加入。`/reload` 后现有村民不会自动更新，可能出现“档案里已禁用，旧村民还在卖”的幽灵交易。

### 2.3 可见性

- 创造栏直接从 `INGREDIENT_TAB_ITEMS` 等数组接受物品，没有统一过滤。
- JEI 只对个别物品做了移除，没有按地区可用性统一隐藏物品、信息页和配方。
- 现有配置只服务东北乐事，不是多地区模型；新分支不能继续把它当作唯一真相。

## 三、四个状态必须分开

| 状态 | 含义 | 典型判断 |
|---|---|---|
| 已注册 | 物品/方块存在于注册表 | 所有 CRCI 内容都注册，保证存档和跨模组一致性 |
| 已安装 | 地区专属内容的拥有模组已加载；CRCI 食材不以某个地区安装为归属条件 | `ModList.isLoaded(owner)` |
| 已启用 | 某地区档案允许这项内容出现在游戏可见范围 | 地区档案的 `enabled_content` 并集 |
| 已投放 | 在某个具体位置允许使用 | 农田池、交易表、战利品表、野生生成表 |

关键点：

- **已启用不等于已投放**。作物可以先启用（可合成、可进创造栏、可进 JEI），但地区档案没有把它放进平原农田或农民交易，它就不会从那些地方出现。
- **地区专属内容未安装是硬门槛**。菜肴、建材、结构这些内容所属地区不在时，其他地区不能代为启用。CRCI 食材则是通用内容，只要某个已安装地区启用它即可。
- 未启用的 CRCI 物品仍然保留注册。否则不同机器之间的注册表 ID 会错位，旧存档也会损坏。玩家用 `/give` 能拿到，这是设计允许的例外。

## 四、地区档案的数据格式

每个地区模组提供一份档案，建议放在：

`data/<地区模组 id>/crci/profile.json`

东北乐事就是 `data/northeast_china_delight/crci/profile.json`。CRCI 启动时扫描所有命名空间下的 `crci/profile.json`，按 `owner` 校验后合并。档案随模组 jar 分发，整合包也可以用一个更高优先级的数据包整文件覆盖它。配置只控制获取途径开关，见第十节。

### 内容分类

在第一版里先固定为四类，避免“归属”和“启用”再次混在一起：

| 类别 | 例子 | 注册位置 | 启用规则 |
|---|---|---|---|
| CRCI 基础内容 | 大脸盆、水盆、大缸、木臼、烤架、锅具、碗 | CRCI | CRCI 安装即用，不需要地区档案启用，也不自动进入交易池 |
| CRCI 食材 | 所有可食用/可加工食材、种子、作物植株，包括只有某个地区才会用到的干辣椒 | CRCI | 由任一已安装地区档案的 `enabled_content` 启用；多个地区取并集 |
| 地区专属内容 | 菜肴、建材、结构、地区装饰方块 | 地区模组命名空间 | 只有拥有它的地区能启用；模组没安装就没有内容 |
| 外部模组内容 | 农夫乐事的稻米、其他前置的食材 | 外部模组 | 不归 CRCI 管；引用的模组已安装即可使用，不要求进入 CRCI 启用表 |

推荐的第一版格式如下（示例只列了必要的几项）：

```json
{
  "schema": 1,
  "owner": "northeast_china_delight",
  "enabled_content": [
    "chinese_regional_culinary_ingredients:napa_cabbage",
    "chinese_regional_culinary_ingredients:soybean",
    "chinese_regional_culinary_ingredients:corn_seeds",
    "chinese_regional_culinary_ingredients:napa_cabbage_seeds"
  ],
  "trade_overrides": [],
  "farm_crops": [
    {
      "seed": "chinese_regional_culinary_ingredients:soybean",
      "full_growth": {
        "Name": "northeast_china_delight:soybean_crop",
        "Properties": { "age": "7" }
      },
      "pools": [
        { "id": "plains", "weight": 8 },
        { "id": "taiga", "weight": 8 }
      ]
    }
  ],
  "trades": {
    "farmer": [
      {
        "level": 1,
        "cost": [
          { "item": "chinese_regional_culinary_ingredients:napa_cabbage", "count": 16 }
        ],
        "result": { "item": "minecraft:emerald", "count": 1 },
        "max_uses": 16,
        "xp": 2
      }
    ],
    "wanderer": [],
    "side_dish": [],
    "butcher": [],
    "fisherman": []
  }
}
```

字段含义：

- `schema`：数据格式版本。以后改字段时用它做兼容迁移，不能让旧档案静默按新语义运行。
- `owner`：地区模组的 mod id。CRCI 只接受已加载模组的档案。
- `enabled_content`：该地区允许进入游戏可见范围的 CRCI 食材，以及该地区自己命名空间下的专属内容。未列出的内容不因“物品恰好存在”而自动可用；多个地区同时启用同一样 CRCI 食材时取并集并去重。
- `farm_crops`：只描述“可以进农田”的作物，和 `enabled_content` 分开。`seed` 是该作物的播种物品 ID，不是植株方块 ID；`full_growth` 是要写入农田的完整方块状态；`pools` 决定气候和权重。
- `trade_overrides`：用 CRCI 默认交易 ID 覆盖职业、等级、价格、数量、最大使用次数等；只能覆盖已启用食材的默认交易。
- `trades`：该地区提供的交易项，按 `farmer`、`wanderer`、`side_dish`、`butcher`、`fisherman` 分组。`cost` 最多两项，对应原版村民交易的两个输入；`result` 是村民给出的物品。买入和卖出不另设方向字段，统一用“成本 → 结果”表达，避免把 `buy`/`sell` 的语义再解释一遍。
- `villager_types`、`guaranteed` 等可选字段按需增加。现有“只在寒冷群系出售”和“大师级必定有黄桃罐头”都应变成数据字段，不再写死在 Mixin 里。

`full_growth` 使用方块状态编码，可以表达 `age`；`result`/`cost` 必须能保留物品组件或 1.20.1 的 NBT，否则现有“半瓶酱油”“带耐久的瓶子”等交易无法无损迁移。这里应复用两个版本树已有的物品栈编解码工具，不要只存物品 ID 和数量。

CRCI 基础内容不写进地区档案，也不需要地区启用。它们由 CRCI 自己的注册表标记为“always available”，因此大脸盆、大缸这类容器不会因为没有任何地区启用而消失，也不会自动进入全局作物交易池。

## 五、归属、冲突与硬门槛

### 5.1 为什么不能只看命名空间

CRCI 食材统一注册在 CRCI 命名空间下（例如 `chinese_regional_culinary_ingredients:chili`），即使只有西南乐事会用到。它们不是“西南乐事的物品”，而是“CRCI 的通用食材，由西南乐事启用”。因此不需要给每样食材建立唯一地区所有者；只需要记录哪些已安装地区启用了它。

地区专属内容才按命名空间判归属：菜肴、建材、结构等必须属于档案的 `owner` 命名空间，其他地区不能在启用表里代持。这样既允许干辣椒被多个已安装地区共同启用，又禁止东北乐事把西南乐事的菜肴塞进自己的档案。

### 5.2 校验顺序

1. `owner` 必须是已加载 mod，否则整份档案丢弃。
2. 每条 `enabled_content`、每个 `farm_crops.seed`、每条交易输入输出都必须是已注册物品；找不到的 ID 记录警告并跳过该条，不让整个服务器启动失败。
3. 对 `enabled_content` 中的每一项分类：
   - CRCI 命名空间：必须出现在 CRCI 的“可启用食材目录”中。大脸盆这类基础内容不允许通过地区档案重复启用，它们本来就是常驻可用。
   - 本档案 `owner` 命名空间：允许，视为地区专属内容。
   - 其他地区命名空间：拒绝，记录冲突日志。地区 A 不能启用地区 B 的菜肴、建材或结构。
   - 外部模组命名空间：不写进 `enabled_content`；交易和配方可以直接引用，运行时只检查该外部模组是否加载。
4. `enabled_content` 取并集。多个地区同时启用同一样 CRCI 食材不算冲突，最终只记一次；干辣椒可以由西南启用，也可以在另一个地区确实需要时由另一个已安装地区启用。
5. `farm_crops.seed` 必须是 CRCI 食材或本地区专属作物，并且已在该档案的 `enabled_content` 中；`full_growth` 的方块必须与 seed 属于同一内容类别。农田池不会因为另一个地区没安装而留下空规则。
6. 交易项可以使用原版物品、已加载外部模组的物品、任一已安装地区启用的 CRCI 食材，以及本地区专属内容。任何一项不可用时整条交易跳过，避免出现半个配方或空产物。
7. CRCI 基础内容始终可用，不参与“没有模组用到”的提示；只有注册在 CRCI、但没有被任何已安装地区启用、也不是基础内容的物品，才显示“没有模组用到这个物品”。
8. 配置只对自然生成、箱子和交易等获取途径开关生效，不改变 `enabled_content` 本身，也不改变物品能否合成。不能在没有任何地区启用时凭空增加新的地区专属内容。

### 5.3 数据包能改什么

- 可以覆盖某个地区的 `profile.json`，删减 `enabled_content`、改农田权重、改交易价格或等级。
- 可以新增一个已安装地区的档案，但不能凭一个未安装 mod 的 id 伪造档案；`owner` 校验会拒绝。
- 不建议让数据包直接改 Java 注册表。注册表仍由模组负责，数据只决定“是否可见、是否投放”。

## 六、运行时结构

建议在 CRCI 中增加四个职责单一的组件：

1. **`CrciRegionProfiles`**：数据重载监听器，解析、校验、合并档案，生成不可变快照。
2. **`CrciAvailability`**：只回答“这个物品在某个使用场景是否可用”，不负责生成或交易。
3. **`CrciContentSync`**：服务端把可用物品集合和档案版本同步给客户端；用于创造栏、JEI 和客户端提示。
4. **`CrciTradeRegistry` / `CrciFarmRegistry`**：把档案中的投放项整理成可查询的农田池和交易池。

`CrciAvailability` 至少提供：

```java
boolean isAvailable(Item item, CrciUseSite site);
boolean isStackAvailable(ItemStack stack, CrciUseSite site);
Set<Item> availableItems(CrciUseSite site);
```

`CrciUseSite` 建议包含 `CREATIVE`、`JEI`、`FARM`、`TRADE`、`LOOT`、`RECIPE`、`WORLDGEN`。这样以后某个场景需要额外收紧时，不必再改一遍所有调用点。

重载时整份快照原子替换；生成、交易和 JEI 始终读取当前快照，不直接读取 JSON，也不直接调用某个地区的静态数组。服务端以服务端档案为准，客户端只接收同步结果，不能拿本地配置自行决定。

## 七、村庄农田的生成改造

### 7.1 不再使用每作物一条 `RuleTest`

`RuleTest` 的接口不够用，不是简单补几个判断能解决的。推荐新增一个 CRCI 的 `StructureProcessor`，例如 `crci:regional_farm_crop`，每个气候的处理器列表只放一条该处理器，而不是 10 到 20 条作物规则。处理器拿得到 `LevelReader` 和当前位置，可以按需读取群系；即使第一版不按群系二次筛选，也能用处理器上下文把“选择一个作物”完整做完。

处理流程：

1. 输入方块仍是原版农田的小麦（之后若要支持胡萝卜/马铃薯，再扩展 `base_blocks`）。
2. 根据处理器配置的 `pool` 找到该气候的活跃作物列表。
3. 对活跃作物做权重随机；未启用、未安装、未在本池中的作物不参与。
4. 随机失败时保留原方块；成功时写入该作物档案里的 `full_growth`。
5. 活跃池为空时安全返回原方块，不产生空指针或把农田挖空。

这样“关闭一个作物”只会影响该作物的权重，不会让替换总概率无谓降低。建议每个池在处理器里保留一个 `replacement_chance`，用它控制该气候的总替换比例；各作物的 `weight` 只决定池内相对比例。

### 7.2 气候池

第一版先固定以下池，和现有世界生成文件一一对应：

| 池 id | 对应处理器列表 |
|---|---|
| `desert` | `minecraft:farm_desert` |
| `plains` | `minecraft:farm_plains` |
| `savanna` | `minecraft:farm_savanna` |
| `snowy` | `minecraft:farm_snowy` |
| `taiga` | `minecraft:farm_taiga` |
| `taiga_small` | `northeast_china_delight:farm_taiga_small`（拆分后迁到 CRCI） |

东北档案把现有 16 种作物按现分配拆到这些池中，权重照当前概率换算。其他地区只在自己的档案里增加 `farm_crops` 或改权重，不修改 CRCI 的处理器 JSON。

如果未来需要“只在森林边缘生成”“只在某种生物群系生成”的农田变体，再给池增加 `biome_tag` 条件；第一版不要把村庄气候和群系条件混在一起，否则很难解释为什么平原村庄里没有作物。

### 7.3 与原版/其他模组的冲突

CRCI 仍然需要覆盖原版 `minecraft:farm_*` 处理器列表。这个覆盖本身是数据包级别的，其他模组如果也整文件覆盖同名列表，仍然会有“最后加载者胜出”的风险，不会因为改成 CRCI 处理器就自动消失。区别是：CRCI 只维护 6 份稳定文件，所有地区共用同一套逻辑，不需要每个地区各写一份规则；其余模组的处理器是否能共存，要靠加载顺序和兼容测试确认。

### 7.4 野生生成不是农田池

桔梗、人参、榛子丛、木耳等野生植物不应塞进村庄农田池。它们需要另一套 `worldgen` 投放表：群系标签、密度、遮挡条件、距同类方块的最小距离等。两套表可以共用 `CrciAvailability`，但不要共用“村庄农田的权重”字段。

## 八、售卖：合并交易池与运行时守卫

### 8.1 统一交易项

CRCI 建立一个全局交易注册表，保存三类内容：

1. **CRCI 默认交易**：每种可交易食材在 CRCI 中登记一个稳定的默认交易 ID，例如 `crci:farmer/buy/soybean`、`crci:farmer/sell/soybean`。地区启用该食材时，默认交易自动进入全局池，不需要地区重复写价格。
2. **地区覆盖**：地区档案可以用默认交易 ID 覆盖职业、等级、价格、数量、最大使用次数等，例如把大豆的收购等级从 1 调到 2。覆盖项仍然只对已启用的食材生效。
3. **地区专属交易**：地区档案直接注入自己的交易项，用于新菜肴、新建材、地区特产等 CRCI 没有默认交易的物品。CRCI 基础容器不自动生成默认交易，但地区若明确写一条交易，CRCI 不阻止。

默认交易池覆盖五类食物相关职业：

| 职业 id | 中文名 | 典型默认交易 |
|---|---|---|
| `farmer` | 农民 | 作物、种子、初级农产品 |
| `wanderer` | 流浪商人 | 稀有种子、地方特产、少量作物 |
| `side_dish` | 副食商 | 加工食材、调料、成品菜 |
| `butcher` | 屠夫 | 肉类、下水、动物油等 |
| `fisherman` | 渔夫 | 鱼、虾、贝类、海参等水产 |

每样食材的默认交易在 CRCI 数据里指定“职业 + 等级 + 买/卖”，而不是让五个职业都卖同一样东西。例如大豆可以同时给农民和副食商，猪肉类只给屠夫，鱼获只给渔夫。地区可以覆盖这些默认项，也可以为自己的专属内容指定五类中的任意职业；其他职业只有地区显式指定时才注入交易。

数据接口示意：

```json
{
  "trade_overrides": [
    {
      "target": "crci:farmer/buy/soybean",
      "level": 2,
      "max_uses": 16
    }
  ],
  "trades": {
    "farmer": [
      {
        "level": 5,
        "cost": [ { "item": "minecraft:emerald", "count": 8 } ],
        "result": { "item": "northeast_china_delight:some_dish", "count": 1 },
        "max_uses": 12,
        "xp": 30
      }
    ],
    "wanderer": [],
    "side_dish": [],
    "butcher": [],
    "fisherman": []
  }
}
```

`target` 必须指向 CRCI 已注册的默认交易 ID；找不到或目标食材未启用时，覆盖项跳过并记录日志。同一个默认交易被多个地区覆盖时，按档案优先级只保留一个最终结果，避免价格随机取决于模组加载顺序。

东北乐事的 `ModFarmerTrades`、`ModWandererTrades`、`SideDishMerchantTrades` 都改成档案数据；`SideDishMerchantTradeMixin` 的“大师级必定黄桃罐头”改成交易项的 `guaranteed` 标记。这样以后西南乐事想“大师级必定卖某样东西”时，不需要再写一个 Mixin。

交易池合并规则：

1. 先收集已启用食材的 CRCI 默认交易，再应用地区覆盖，最后加入地区专属交易。
2. 每个条目先检查成本、结果、可选取货容器是否可用；任何一项不可用就整条跳过。
3. 副食店和副食商由 CRCI 提供，每个村庄最多生成一个；副食商不按店铺地域隔离，所有已启用地区的交易项进入同一个池，不同地区的商品可以混卖。
4. 如果只安装 CRCI、没有任何地区乐事，则不生成副食店，也不生成副食商；只有至少一个地区安装并提供副食交易项时才启用。
5. 同一物品的完全相同交易项应去重，避免两个地区档案重复添加同一笔交易；不同价格/等级的交易允许保留，但要在加载日志里提示。
6. 原版村民每级仍然只随机抽两条，CRCI 不改变原版抽取规则；交易条数增加后，单条出现概率自然下降。

### 8.2 在 `getOffer()` 再判断一次

只在 `VillagerTradesEvent` 触发时过滤不够。`/reload` 或配置重载后，池子会变，但已经生成的村民仍持有旧的 `MerchantOffer`。每个交易项应包一层 `AvailabilityGuardedListing`：

```java
public MerchantOffer getOffer(Entity trader, RandomSource random) {
    if (!CrciAvailability.isTradeAvailable(entry)) {
        return null;
    }
    return delegate.getOffer(trader, random);
}
```

原版 `AbstractVillager#addOffersFromItemListings` 会跳过 `null` 并继续抽下一条，因此守卫返回 `null` 不会破坏村民生成。这样即使事件早已触发，过期的交易项也不会再被新村民选中。

### 8.3 旧村民和流浪商人的清理

为了满足“未安装内容完全不可知”，还需要在档案版本变化或 `/reload` 后清理现有实体：

- 遍历已加载世界的村民和流浪商人，从其 `MerchantOffers` 中移除成本或结果不可用的条目；
- 若玩家正在与该商人交易，关闭交易界面或重新发送剩余报价；
- 对已经存在的旧存档，不清除村民本身，只清理不应存在的报价。

这一步是必要的，否则会出现“JEI 和创造栏已经隐藏，但旧村民还在卖”的不一致。

### 8.4 JEI 与 ALI

JEI 的交易条目和高级战利品显示（ALI）不能继续读硬编码的 `tradeListingArrays()`。它们应读取同一个 `CrciTradeRegistry` 快照，并套用与运行时相同的可用性判断。否则展示端会出现已经禁用或未安装地区的商品。

## 九、可见性：从“生成时过滤”扩展到“完全不可知”

### 9.1 创造模式物品栏

- `addItemsToCreativeTab` 在加入每个 `Item` 前调用 `CrciAvailability.isAvailable(item, CREATIVE)`。
- 服务端与客户端必须使用同一份同步快照；不能只在服务端过滤，否则联机客户端仍会显示。
- 档案在游戏启动前已读取时，创造栏第一次构建就可以正确过滤；`/reload` 后的创造栏刷新可能受原版缓存影响，第一版可以要求重新登录/重启客户端，并在文档里写清楚。
- 未启用物品仍可用 `/give` 获得，这是为了注册表一致性和存档兼容，不能为了创造栏隐藏而取消注册。

### 9.2 JEI

至少要做四件事：

1. 从 `IIngredientManager` 移除未启用物品的所有 `ItemStack`；
2. 隐藏产物不可用的配方；
3. 隐藏必需输入不可用的配方；标签输入只有在标签内没有任何可用替代品时才隐藏，不能因为标签里有一个禁用项就整条隐藏；
4. 隐藏未启用物品的信息页、催化剂页和交易页。

第一版可以先把 CRCI 自己的分类全部接上，再要求每个地区乐事通过同一个 `CrciJeiFilters` 判断自己的配方。否则第三方 JEI 插件仍可能展示引用未启用物品的配方，不能宣称“完全不可知”。

### 9.3 配方书与配方注册

已确认采用方案 A：**地区乐事只控制自然生成、战利品和村民交易等获取途径，不控制 CRCI 物品的合成能力**。

- 配方继续正常注册，玩家用 `/give` 取得禁用物品后仍可在工作台、厨锅、大缸等设备里使用和合成。
- 配方书、JEI 和创造栏仍然按可用性隐藏，避免正常玩家从展示端发现未启用内容。
- 不额外实现“禁用物品不能参与配方”的全局过滤层，因此不需要为配方书或已有机器输入做高风险 Mixin。
- “没有模组用到这个物品”的提示只说明正常获取渠道不存在，不表示物品不能使用。

### 9.4 战利品与其他展示面

- `ChestLootConfigModifier` 改为按 `CrciAvailability` 判断，不能再用命名空间白名单。
- 村庄种子、结构种子、钓鱼、猪掉落、木臼/大缸产物等所有注入器都在产出前检查可用性。
- Jade、ALI、进度图标等展示面也要过滤，否则会从提示或进度树泄露隐藏内容。
- 对已有村民报价的清理见第八节；对已生成区块不回溯，文档必须说明“只影响新生成区块”。
- 卸载地区模组时，它的菜肴、建材、结构等专属内容按游戏正常机制删除；不额外在 CRCI 注册占位。
- 旧存档里已经存在的 CRCI 食材保留，不自动删除；若没有任何已安装地区启用它，就在物品信息里显示“没有模组用到这个物品”。地区重新安装并启用后，提示自动消失；CRCI 基础容器和工具不显示这条提示。

## 十、配置与数据包的优先级

建议的优先级从高到低：

1. **注册门槛**：物品/方块必须存在；不存在的内容无法通过配置显示；
2. **地区专属门槛**：地区专属内容（菜肴、建材、结构）必须由拥有它的 mod 提供，mod 未安装就直接不可用；
3. **CRCI 基础内容**：大脸盆、大缸等常驻可用，不依赖地区启用；
4. **档案启用**：合并所有已安装地区的 `enabled_content`，决定哪些 CRCI 食材进入可见内容和获取候选；地区专属内容只接受本地区启用；
5. **获取途径开关**：配置只控制农田替换、箱子注入、村民交易等获取途径是否启用；
6. **运行时使用场景**：`CREATIVE`、`JEI`、`LOOT` 等再做最后判断。

配置不控制 CRCI 物品能否合成，也不新增 item 级“强制启用/强制禁用”矩阵。第一版只需要：

- `worldgen.village_farm_crops_enabled`：是否允许 CRCI 作物替换村庄农田；
- `chest_loot.enabled`：是否允许 CRCI 物品进入箱子战利品；
- `trades.enabled`：是否允许 CRCI 默认交易和地区交易进入村民池。

如果以后确实需要服务器级物品过滤，再单独加一层，不把它混进地区档案。配置在每次启动/重载时重新读取；旧版 `village_farm_allowed_crops` 与 `chest_loot.allowed_items` 只作为迁移参考，不作为新模型的唯一真相。

## 十一、迁移顺序

### 阶段 A：CRCI 核心（先不迁移全部内容）

- 定义 `profile.json` 的 codec、版本号和错误处理；
- 建立 `CrciAvailability`、快照重载、服务端 → 客户端同步；
- 用一两个物品做“未安装即隐藏”的 GameTest；
- 建立 CRCI 的“基础内容”和“可启用食材”目录，确认没有“未启用食材默认可见”的漏洞。

### 阶段 B：农田样板

- 新增 `regional_farm_crop` 处理器；
- 先只迁移玉米或大豆，保持其余规则暂不动；
- 对比旧行为：同种子、同气候、替换比例接近；
- 确认关闭该作物后原版小麦保留，且其他作物概率不塌陷。

### 阶段 C：迁移全部东北作物

- 把 16 种作物的 seed、full_growth、气候池和权重写入东北档案；
- 删除 `VillageFarmCropRuleTest` 和逐作物规则；
- 保留 6 个气候处理器文件作为 CRCI 的标准入口；
- 更新 `自然生成配置.md` 的说明，避免继续把旧的单一名单当成唯一入口。

### 阶段 D：交易迁移

- 先迁移农民和流浪商人，验证买入/卖出、价格、等级和物品组件；
- 再迁移副食商，验证跨地区混卖和大师级保底；
- 接着迁移屠夫和渔夫，验证肉类、下水、水产的默认交易；
- 把 `SideDishMerchantTradeMixin` 的黄桃罐头逻辑改成数据；
- 更新 JEI、ALI 和现有交易文档。

### 阶段 E：完整可见性与旧存档

- 创造栏、JEI、配方书、战利品、进度逐个接入；
- 清理旧村民报价；
- 做 1.21.1 与 1.20.1 两棵树的同语义测试；
- 最后回归五类食物相关职业的默认交易、地区覆盖和专属交易。

## 十二、工作量估算

按一个人开发、编译由你这边执行估算，不含美术和配方数值调整：

| 工作块 | 估算 |
|---|---:|
| 档案 codec、归属/冲突、可用性快照、客户端同步 | 2~3 天 |
| 农田处理器、气候池、16 种作物迁移与兼容测试 | 2~3 天 |
| 交易注册表、五类职业迁移、守卫与旧报价清理 | 5~6 天 |
| 创造栏、JEI、配方书、战利品、ALI/Jade 过滤 | 3~5 天 |
| 双版本适配、GameTest、文档和回归 | 2~3 天 |
| **合计** | **14~20 天** |

如果第一版只做“作物启用 + 农田生成 + 五类食物相关职业售卖”，暂不处理配方书和所有展示端，大约 **9~12 天**；但这时不能对外宣称“未安装内容完全不可知”，只能宣称“正常获取渠道不可见”。

## 十三、验收清单

- [ ] 只安装 CRCI：仅由地区启用的食材和地区专属内容不出现在创造栏、JEI、交易、箱子、农田和野生生成；不生成副食店和副食商；
- [ ] 安装东北乐事但档案只启用大豆：大豆可见、可合成、按配置进农田和交易；玉米等其他内容不可见；
- [ ] 启用两种作物但只把一种放进平原池：平原农田只出现这一种，另一种仍可用于合成；
- [ ] 关闭某个气候池：该气候的原版作物不被替换，服务器不报错；
- [ ] 两个地区同时安装：副食商交易池合并，交易项不重复，未启用地区仍不可见；
- [ ] 未安装地区的数据包残留：`owner` 校验拒绝，不产生任何内容；
- [ ] 农民、流浪商人、副食商、屠夫、渔夫的交易成本/结果任一不可用时，整条交易不生成；
- [ ] 作物默认进农民/流浪商人/副食商，肉类默认进屠夫，水产默认进渔夫，不会五个职业都卖同一样东西；
- [ ] 启用 CRCI 食材会自动生成默认买卖交易，地区覆盖生效，地区专属交易可以注入；
- [ ] 用 `/give` 取得未启用物品后仍可合成和使用，但不会出现在正常展示端；
- [ ] `/reload` 后旧村民不再出售已禁用内容；
- [ ] 专用服务器客户端收到的可用集合与服务端一致；
- [ ] 1.21.1 与 1.20.1 的语义一致，只有 API/编解码实现不同；
- [ ] 关闭农田替换或箱子注入时，原版与农夫乐事的内容不受影响。

## 十四、推荐落地方式

先实现阶段 A 和阶段 B，不要立刻删除全部旧交易。原因是：

- 数据格式一旦发给建模师、整合包作者和其他地区开发者，就会变成对外契约；
- 农田处理器、客户端同步和 JEI 过滤是三套独立风险，分开验证更容易定位问题；
- 东北乐事旧分支已经冻结，新分支可以先保持旧交易代码，等新注册表通过样板验证后再迁移。

如果只问“能不能让地区乐事决定作物生成和售卖”，答案是能；代价主要不在注册物品，而在**统一归属、重写农田投放入口、把所有交易从 Java 搬到数据、以及同步清理客户端和旧存档的展示**。这四件事做完，未来新增一个地区只需要提供自己的档案和内容，不需要再改 CRCI 的生成器或交易类。
